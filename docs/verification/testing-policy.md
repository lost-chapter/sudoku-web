# テストの方針

**このプロジェクトで最も守りたいのは「収録した問題がすべて一意解であること」である。**
壊れた問題を配ってしまうと、遊技者は自分の入力を疑い続けることになる。

テストの重心は `packages/core`(盤面ロジック)に置く。
画面のテストは薄くてよいが、**盤面ロジックのテストは薄くしない**。

## 層ごとの方針

| 層 | 何を守るか | 手段 |
|----|-----------|------|
| `core` | 盤面の規則・ソルバ・生成・難易度評価 | 単体テスト。**ここが主戦場** |
| `generator` | パックとマニフェストの出力が契約どおりか | 少数の問題を実際に生成して検証 |
| `web` | 状態遷移(入力・メモ・取り消し) | `core` の reducer に対する単体テスト |
| `web`(描画) | 主要な操作が動くこと | 少数に絞る。**網羅しない** |
| `web`(E2E) | **本物のキーイベントでしか起きないこと** | Playwright。**3 件だけ**(下記) |

**描画のテストを増やしすぎない。** 壊れやすく、壊れたときに得られる情報が少ない。

### E2E は「代わりが無いもの」だけに使う

**`pnpm test` と `pnpm test:e2e` は別である。** E2E は Vitest と混ざらないよう
`*.e2e.ts` に置き、`packages/web/e2e/` から `pnpm test:e2e` で回す。

⚠️ **E2E をここから広げない。** 盤面の遷移(選択・入力・メモ・取り消し)は
reducer のテストで押さえてある。**二重に持つと遅く壊れやすくなるだけである。**

**入れてよいのは、他の手段では原理的に確かめられないものに限る。**
2026-08-05 時点では次の 2 種類しかない。

| 何を | なぜ E2E でしか見られないか |
|------|------------------------|
| **Enter / Space でボタンが起動する** | ブラウザ面から送る合成キーでは**ネイティブの活性化が起きない** |
| **モーダルを閉じるとフォーカスが戻る** | JS で開くと「開く前のフォーカス」が無く、`returnFocus` を試せない |
| **1 画面に収まり、盤面とキーが指で押せる大きさである** | **レイアウトが確定しないと高さが出ない**(2026-08-06 に追加) |
| 🔴 **レイアウトが切り替わっても遊技が続く** | **本物の寸法変更でしか起きない**(2026-08-06 に追加。下記) |

**この 4 点は、E2E を入れるまで「人が手で触るしかない」項目だった。**
CI に入れたので、壊れたら気づける。

### 🔴 幅を固定して回す検査は、切り替えを見ていない(2026-08-06)

**幅を広げただけで、入力も保存も消え、別の問題が出た**
([ADR 0005](../decisions/0005-mobile-dedicated-layout.md))。

⚠️ **E2E 33 件が通っていたのに見つからなかった。**
**project ごとに幅を固定して回しており、切り替えが 1 度も起きていなかった。**

**⇒ 見るのは 3 つ ——「入力が残っている」「保存が残っている」「同じ問題である」。**
⚠️ **「描画が壊れていない」では足りない。** **別の問題が出ても、描画は正常に見える。**

**回すのは `phone` の 1 つだけでよい。** 中で自分から寸法を変えるので、
**どの寸法から始めても見るものは同じ**になる。

### 🔴 目で見て正しく見えても足りない(2026-08-06)

**あきらめたときにモーダルが 2 枚重なり、手前しか見えなかった。**
**画面は正しく見えたが、読み上げには「完成しました」が出ていた**
([画面構成と操作仕様](../ui/screens-and-interactions.md))。

⚠️ **E2E 21 件が通っていたのに見つからなかった。**
レイアウトの寸法とキーボードしか見ておらず、**あきらめる経路を誰も通っていなかった。**

**⇒ 状態が変わる操作を確かめるときは、`aria-live` の中身も一緒に見る。**

⚠️ **検査は「モーダルが 1 つだけ」ではなく「完成の知らせが出ない」を見ること。**
**前者は数を数えるだけで、意味を見ていない。**

### E2E の設定で踏んだこと(2026-08-05)

| 落とし穴 | どうしたか |
|---------|-----------|
| **動いているサーバを再利用すると、無関係なサーバに当たっても走る** | `reuseExistingServer: false`。塞がっていれば「already used」で名指しで止まる。**3 件とも原因不明の失敗になるのを実際に再現した** |
| **Vite は塞がったポートを避けて別の番号で起動する** | `--strictPort` を付ける。付けないと Playwright が指定ポートを待ち続け、**分かりにくいタイムアウト**になる |
| **`test-results/` は Git 管理外でも Prettier は見に行く** | `.prettierignore` へ足す。**Prettier は `.gitignore` を読まない**。E2E を回したあと `pnpm format:check` が落ちて気づいた |

## 🔴 検査を回しても、終了コードを見ていないことがある(2026-08-06)

**`docs:lint` は落ちていた。それに気づかず commit した。**

```bash
pnpm docs:lint >/dev/null; echo "docs=$?"   # ← これは見えている
pnpm docs:lint 2>&1 | tail -2 && git commit # 🔴 これは見えていない
```

⚠️ **`| tail` を挟むと、終了コードは `tail` のものになる。**
**検査が落ちても `&&` の右側は走る。**

🎯 **管理役と作業エージェントが、独立に同じ形を書いていた。**
**どちらも「出力を目で読んで判断していた」だけで、終了コードは見ていなかった。**

⚠️ **たまたま気づけたのは、この検査の出力が短くて流れなかったからである。**
**出力が長い検査なら、落ちているのに「通った」と報告していた。**

**⇒ これも「取れたものが、測りたかったものとは限らない」の一種である。**
**見ていたのは出力であって、合否ではなかった。**

| ❌ | ✅ |
|---|---|
| `pnpm docs:lint \| tail -2 && ...` | `pnpm docs:lint && ...`(**パイプを挟まない**) |
| `検査A; 検査B \| tail -1` | `検査A && 検査B`(**`;` で繋がない**) |
| 出力を読んで判断する | **`echo "$?"` を出す**か、**`&&` で繋いで落ちたら止める** |

⚠️ **出力を絞りたいときは、終了コードを別に出す。**

```bash
pnpm docs:lint > /dev/null; echo "docs:lint=$?"
```

## 🎯 検査は結論から選ぶ(2026-08-06)

**「検査を持っている」ことと「正しい検査を選んでいる」ことは別である。**

⚠️ **通っている検査は、それだけでは何も保証しない。**
**その検査が通ったとき何が言えるのか**を先に決め、**言いたいことを言える検査を選ぶ。**
順序が逆になると、**測りやすいものを測って安心する**ことになる。

### 🎯 選ぶときの条件: 「いつ実行しても意味が変わらないか」

**下の 2 例も、`ops-release` の完了条件も、外したのは同じ点だった。**

| どこで | 選んだ検査 | いつまで成り立つか |
|--------|-----------|------------------|
| 強調の修正 | `<strong>` の数が減っていない | ⚠️ **その修正作業の最中だけ** |
| リリースの完了条件 | `git diff develop main` が空 | ⚠️ **リリース直後だけ**(`develop` が進むと崩れる) |
| リリースの完了条件 | `git log develop..main` が空 | 🔴 **一度も成り立たない**(マージコミットが必ず残る) |

**⇒ 検査を選ぶときは「あとから同じものを実行しても、同じ意味になるか」を問う。**
⚠️ **その瞬間だけ成り立つ条件は、正しい状態を未完了に見せる。**
**次に確かめた人が、無いはずの問題を探し始める。**

### 実例 1: 数が同じことは「消えていない」の証明にならない

`.md` の強調を 128 か所直したとき、最初は
**変換後の HTML に出る `<strong>` の数が減っていないこと**で確かめるつもりだった。

⚠️ **これは「直す」ときにしか使えない検査だった。**
同じ作業で**規則の文書へ節を書き足した**ところ、`<strong>` は当然増える。
**増えたのが追記のぶんなのか、別の場所が強調に化けたのかを区別できない。**

**⇒ 検査を「タグと空白を除いた本文が完全に一致すること」へ選び直した。**
約物を動かしただけなら本文は 1 文字も変わらない。**これは「何も失っていない」を直接示す。**

実測(2026-08-06 の 3 文書)では **`<strong>` は 137 → 138 と増えた**が、
**本文は 3 文書とも完全に一致した。** 増えたのは意図した 1 か所である。

🎯 **足すときと直すときで、見るべきものが違う。**

### 実例 2: 包含関係で比べると「差あり」が出続ける

統合の差分を確かめるとき、**片方の文字列がもう片方を含むか**(`includes`)で比べて
**実際には同じ内容なのに「差あり」と判定した。**

⚠️ **包含は「一致」ではない。** 順序や重複の違いを拾えず、
**通っても何が言えるのかが定まらない。**

**⇒ 行単位の比較へ直した。** 「どの行が増え、どの行が減ったか」が出るので、
**差が出たときにそのまま次の判断へ使える。**

### 実例 3: 実装のしきい値を検査へ持ち込まない

**「スクロールしない」の E2E に、実装のしきい値(442)を書かない**
([ADR 0005](../decisions/0005-mobile-dedicated-layout.md))。

```js
// ✅ この端末でどうなってほしいか、を固定する
test("390×664 では縦スクロールしない", ...)

// ❌ 実装を変えるとテストも一緒に動き、壊れても落ちない
if (height >= THRESHOLD) { expect(noScroll) } else { ... }
```

**しきい値を動かしたらテストが落ちる —— それが正しい姿である。**
実装を参照した瞬間、**その検査が言えるのは「実装は実装どおり」だけになる。**

### 選んだ検査に検出力があるかを確かめる

**「0 件だった」「全部通った」だけでは、検査が効いているのか区別が付かない。**

**⇒ わざと壊して、落ちることを見る。**

| いつ | 何を壊したか | 結果 |
|------|------------|------|
| あきらめる機能 | `isSolvedByPlayer` を `matchesSolution` へ戻す | E2E と単体テストの両方が落ちた |
| モーダルのフォーカス | `returnFocus={false}` にする | E2E が落ちた |
| 和文の強調の検査 | 段落単位をやめて行単位へ戻す / 約物の判定を外す / コードスパンの除外を外す | 14 件中それぞれ 2 / 6 / 2 件が落ちた |

⚠️ **落ちなかったら、その検査は目的のものを見ていない。**

## 🔴 取れたものが、測りたかったものとは限らない(2026-08-06)

**上の 3 例は「検査の選び方」だった。こちらは「測る対象の取り方」である。**

⚠️ **同じ日に 3 回起きた。どれもエラーが出ず、値だけが嘘だった。**

| 何をした | 取れたもの | 測りたかったもの | どうなったか |
|---------|-----------|----------------|------------|
| `pad1.closest("div[class]")` でパッド領域を取る | **数字の行だけ** | 数字 + 補助行の全体 | **補助行 64px を「空白」と読み違え**、要らない改修を指示しかけた |
| 入力パッドのキーを 1 つ測って代表とする | **パッドの 1 つ目** | 画面上の押せるもの全部 | **ホーム画面の 36px を見逃した** |
| `git log develop..HEAD` で未統合を数える | **古い `develop` との差** | いまの `develop` との差 | **統合済みの 3 件を「未統合」と報告した** |

🎯 **どれも取得そのものは成功している。** だから例外も警告も出ない。
**返ってきた値を見ても、それが目的のものかどうかは分からない。**

**⇒ 対策は 2 つあるが、効く範囲が違う。**

🎯 **本命は「取れたものが期待どおりかを、値とは別に確かめる」。**
**上の 3 例すべてに効く。**

| 何を取ったか | 値とは別に確かめること |
|-------------|---------------------|
| パッド領域 | **「取り消し」を含んでいるか** |
| 押せるもの | **数が画面上のボタンの数と合っているか** |
| `develop` | **どのコミットを指しているか**(`git log -1 develop`) |

**もう 1 つは「代表を取らず、全部走査する」。**
⚠️ **ただし走査で置き換えられる形のときにしか使えない。**
**上の 3 例のうち、これで防げるのはボタンの 1 例だけである**
(`closest` も `develop` も、走査する対象が無い)。

⚠️ **「同じ作りのものが並んでいる」という前提が要ることにも注意する。**
**画面が違えば作りも違うので、代表を取ってよい範囲は思うより狭い。**

⚠️ **これは [コントラストの測り方](../ui/screens-and-interactions.md) で
3 回踏んだ「測定器は落ちずに嘘の値を返す」と同じ構造である。**
**あちらは色の読み違い、こちらは対象の取り違いで、**
**どちらも「落ちないので気づけない」ことが本体である。**

## 和文の強調は機械で見張る(2026-08-06)

**規則を書いただけでは止まらなかった。**
`.md` の 128 か所を直し、[ドキュメント管理規則](../guides/documentation-guidelines.md) へ
書き方を足した**後に書かれた文章**で、**さらに 8 か所が同じ形で壊れていた。**

⇒ **人が気をつける話をやめて、検査にした。**

```bash
node tools/docs-lint/check-emphasis.mjs          # docs/ + AGENTS.md + README.md + SKILL.md
node tools/docs-lint/check-emphasis.mjs a.md     # ファイルを指定
```

| 性質 | 中身 |
|------|------|
| **見るのは「閉じられるか」だけ** | 強調の付け方が適切かは見ない。**それは人が読んで決めること** |
| **段落単位で見る** | ⚠️ **行で切ると、2 行にまたがる正しい強調を誤検知する**(実際に 1 件踏んだ)。**初日から落ちる検査は誰も見なくなる** |
| **表の行と見出しは 1 行で 1 つの塊** | まとめると隣の行の `**` で閉じたことになり、**壊れているのに見逃す** |
| **コードスパンとコード塊は見ない** | ⚠️ **規則の文書が壊れた書き方を例示している。** 拾うと「直せない検査」になる |
| **見つかったら終了コード 1** | CI から素直に使える |

検出力は `tools/docs-lint/check-emphasis.test.mjs`(**14 件**。`pnpm test` に含まれる)で固定する。
**依存を足していない**(Node 標準の `node:test`)。

## 必ず守る性質

**個別の入出力ではなく「性質」でテストする。**
生成はランダムなので、固定の期待値では守れない。

| # | 性質 | 検証のしかた |
|---|------|------------|
| 1 | **生成した問題は一意解である** | 生成の直後にソルバで解の個数を数え、1 であること |
| 2 | **手がかりを 1 つでも消すと一意解でなくなる**(極小性を謳う場合) | 各手がかりを 1 つずつ戻して複数解になることを確認 |
| 3 | **同じシードからは同じ問題ができる** | 2 回生成してバイト単位で一致すること |
| 4 | **難易度の判定が安定している** | 同じ問題を 2 回評価して同じクラスになること |
| 5 | **解いた結果が数独の規則を満たす** | 行・列・ブロックに 1〜9 が 1 個ずつ |
| 6 | **パックの全問が読み込める** | 収録済みパックを全件パースして検証 |

**1 と 3 は落としてはいけない。** 1 は製品の正しさ、3 は再現性の土台
([ADR 0003](../decisions/0003-external-puzzle-files.md) は「シードから作り直せる」ことに依存している)。

## 収録前の検証

**問題は「生成した」だけでは収録しない。** パックへ入れる前に次を通す。

1. 一意解であること
2. 難易度クラスがマニフェストの宣言と一致すること
3. 形式が [問題ファイルの形式](../api/puzzle-file-format.md) の契約を満たすこと

**1 つでも落ちたら、その問題を捨てる**(パック全体を捨てない)。

## 回帰の防ぎ方

- **既知の壊れた入力はテストへ固定する。** 不具合を直したら、その盤面を残す
- **`core` を変えたら生成側と遊技側の両方のテストを回す。**
  同じソルバを共有しているため、片方だけでは足りない
  ([システム構成](../architecture/system-architecture.md))
- **性能の下限を決めて測る。** 生成が遅くなったことに気づけるようにする
  (基準値は工程 2 で実測してから決める)

## 実装した手筋が本当に発火しているかを見る

**テストが通っていても、その手筋が 1 度も使われていないことがある。**

2026-08-05 に XY-Wing を実装したとき、条件を 1 つ書き間違えて
**1 件も検出しない状態**になっていた。テストは通っていた
(他の手筋で解けてしまうので、結果は変わらなかった)。

**気づけたのは分布を測ったからである。**
「XYZ-Wing は 5.4% 出るのに XY-Wing が 0%」という並びが不自然だった。

**⇒ 手筋を足したら、出現率を測って 0% でないことを確かめる。**

| 手筋 | 出現率(5,000 問) | 手筋 | 出現率 |
|------|------------------|------|--------|
| Hidden Single | 99.3% | X-Wing | 4.0% |
| Naked Single | 95.8% | Swordfish | 1.2% |
| Pointing | 52.9% | Jellyfish | 0.1% |
| Claiming | 25.5% | XY-Wing | 9.8% |
| Naked Pair | 22.3% | XYZ-Wing | 5.4% |
| Hidden Pair | 15.1% | X-Chain | 13.1% |
| Naked Triple | 3.8% | Hidden Triple | 1.1% |
| Naked Quad | 0.1% | **Hidden Quad** | **0.0%** |

⚠️ **0% だからといって、すぐ誤りとは限らない。**
Hidden Quad は実装が正しくても出番が無い(この分布では他の手筋が先に効く)。
**「0% なら実装を疑う」ではなく「0% の理由を説明できるようにする」** のが要点である。

測り方は [難易度クラスの分布](../reports/2026-08-05-difficulty-distribution.md) を参照。

## パックの再現性は CI で見張る

**[ADR 0003](../decisions/0003-external-puzzle-files.md) は
「管理外のパックはシードから作り直せる」ことに依存している。**
ここが壊れても、**収録済みのパックを読むだけのテストでは気づけない。**

CI の「パックの再現性」ジョブが、**収録済みのパックを作り直して `diff` を取る**。

- **ワーカー数を収録時と変えて回す**。「並列度を変えても中身が変わらない」も同時に見る
- 回すのは `easy`(最も安い)と `extreme`(実装している手筋を全部通る)の 2 つ
- **手筋を実装したら、パックを作り直してからコミットする。**
  作り直しを忘れるとこのジョブが落ちる(それが目的である)

### ⚠️ 少ない問数で作り直したものは「先頭が一致」しない

**パックは難易度クラスとスコアの昇順で書く**(採用した順ではない)。
そのため **200 問で作り直したものは 1,000 問版の先頭 200 行ではなく、全体に散らばる**。
実測では先頭 200 行のうち 169 行が違った。

**代わりに「部分集合か」を見る。**
採用は試行番号の昇順で決まるので、**200 問版は「1,000 問版が採用した先頭 200 個」と
必ず同じ集合になる**(実測でも 200 問すべてが 1,000 問版に含まれていた)。

| 何を回すか | 何を見るか | 手元の実測 |
|-----------|-----------|-----------|
| `easy` 1,000 問 | **1 バイトも違わないか**(並び順まで見る) | 3.2 秒 |
| `extreme` 200 問 | **収録済みに全部含まれるか**(集合として見る) | 2.3 秒 |

**`extreme` を 1,000 問にすると 6 倍かかる**(2.3 秒 → 13.1 秒)。
採用率が 5.5% しかないためで、**並び順は `easy` の側で見ているので足りる。**

## 性能を測るときの約束

**測り方を書かない数値は、他の人が再現できない。** 次の 4 つを必ず添える。

| 項目 | なぜ要るか |
|------|-----------|
| **どう実行したか**(`node` / Vitest / tsx) | ⚠️ **Vitest だけ 5〜7 倍遅い**(下記)。`node` と `tsx` はほぼ同じ |
| `load average` | 他の作業と同時に測ると数倍ぶれる |
| 機械と Node のバージョン | 比較の前提 |
| **2 回以上流した値** | 1 回だけだと外れ値と区別できない |

⚠️ **Vitest の上で測った速度を製品の性能として引用しない。**

Vitest(vite-node)は module をまたぐ呼び出しを名前空間のプロパティ参照へ書き換えるため、
**内側のループで何万回も呼ぶ関数が最適化されなくなる**。
実測では同じコード・同じ負荷で **`node` 1.5 ms/問・`tsx` 1.7 ms/問 に対し Vitest 7.9 ms/問**、
**`core` を 1 ファイルに束ねると Vitest でも 1.1 ms/問**に戻った
([検証](../reports/2026-08-05-puzzle-generation-benchmark.md))。

**⇒ 生成器の速さは次の 1 行で測る**。実行のしかた・機械・`load average`・
2 回ぶんの値がまとめて出るので、**報告にはこの出力をそのまま貼る。**

```bash
pnpm --filter @sudoku/generator bench
```

遊技側の速さは本番ビルド(束ねた形)で測る。

**性能をテストに入れるなら、閾値は実測の 3 倍以上に取る。**
そうしないと、他のセッションが動いているだけで落ちる。

## 🔴 閾値が 2 つあるとき、片方だけを見ると穴が見えない(2026-08-06)

**上フリックの閾値を 24px にした。** 実装もテストもその値で正しく動いていた。
**それでも「押したのに何も起きない」領域が 15〜24px にできていた。**

⚠️ **ブラウザ側にも閾値があった。** `click` の合成は
**tap slop(およそ 15px)を超えた動きでやめられる。**

| 上への移動 | 誰が決めているか | 起きること |
|-----------|----------------|-----------|
| 0〜15px | ブラウザ(slop の内側) | `click` が出る → 確定入力 |
| **15〜24px** | 🔴 **どちらの担当でもない** | **`click` は出ず、フリックにも届かない** |
| 24px 以上 | アプリ(`FLICK_DISTANCE`) | フリック → メモ |

🎯 **アプリの閾値だけを見ていると、この隙間は見えない。**
**「閾値の直下は今までどおり動く」という前提が、暗黙にもう 1 つの閾値を仮定している。**

### 切り分けは対照実験で行う

**「フリックのせいか」を確かめるのに、フリックを外して測り直す必要は無かった。**
**フリックの手当てが無いボタン(ホーム画面の難易度)で同じ動きをすれば足りる。**

| 対象 | 上へ 20px |
|------|----------|
| 数字キー(フリックあり) | 何も起きない |
| **難易度ボタン(フリックなし)** | **何も起きない** ← **原因はフリックではない** |

⚠️ **同じ版の中に「効いていないはずの対象」を探す。**
**前の版をビルドし直すより速く、環境の違いも入らない。**

### 合成イベントは本物と違う

**報告では「20px は確定入力になる(拾わない)」だった。実測では何も起きなかった。**
⚠️ **ハンドラの分岐を確かめるだけなら、その報告は正しい。**
**しかし遊ぶ人が触るのはブラウザであって、ハンドラではない。**

**タッチを本物に近い形で送る**(CDP の `Input.dispatchTouchEvent` で
`touchStart` → `touchMove` → `touchEnd`)。

⚠️ **読み取り側にも罠がある。** 空のセルを `.first()` で取ると、
**入力が入った瞬間に別のセルを指す。**
**最初に 1 つ掴んで、以後はその要素だけを見る**(「取れたものが、測りたかったものとは限らない」)。

## 進捗の測り方

[並列エージェントの運用](../guides/parallel-agent-operations.md) に従い、進捗は数値で出す。

- テストの件数と成否
- 型チェック・Lint のエラー数
- **生成の実測**(1,000 問あたりの所要時間、難易度クラスの分布)

**難易度の分布は毎回記録する。** 生成器を変えたときに、
分布が偏っていないかを見る唯一の手段になる。
