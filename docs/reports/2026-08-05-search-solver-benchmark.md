# 検証: 探索ソルバの所要時間(TypeScript)

## 目的

**公開されている性能値がすべて C++ / Java のものだったため、TypeScript 実装で実測する。**
同じ出典に「JavaScript 版は非常に遅い」とあり、
[盤面の生成](../algorithms/board-generation.md) と [解法(ソルバ)](../algorithms/solver.md) の
どちらにも「工程 2 で実測する」と書いてあった宿題である。

**知りたいのは 1 点。**[穴あけ](../algorithms/board-generation.md#2-穴をあける)は
1 マス消すごとに `countSolutions` を回すので、**一意解の判定が生成の律速になるかどうか**。

## 実施日・条件

| 項目 | 値 |
|------|-----|
| 実施日 | 2026-08-05 |
| 対象コミット | `e3005c2`(`packages/core` の `board.ts` と `search-solver.ts`) |
| 実行環境 | Apple M1 Ultra / Node.js v24.18.0 |
| 測り方 | 50 回の暖機後、同じ盤面を 200〜1,000 回解いた合計時間を回数で割る |
| 実行回数 | 3 回(下表は 3 回の幅) |

**計測は本体のテストに含めていない。** 実行時間は機械と同時実行に左右され、
テストとして固定すると偽陽性になる(下記「残課題」)。

## 使用データ

`packages/core/src/test-puzzles.ts` の固定盤面。いずれも一意解であることを実測済み。

| 呼び名 | 手がかり数 |
|--------|-----------|
| 手がかり 30 | 30 |
| 手がかり 23 | 23 |
| 手がかり 17 A / B | 17(一意解を持つ最小) |

比較用に**空の盤面**(手がかり 0)と、
**探索に対して敵対的な盤面**(手がかりが左上に偏った複数解の盤面)も測った。

## 結果

| 盤面 | `solveBoard`(解を 1 つ) | `countSolutions`(上限 2) |
|------|------------------------|--------------------------|
| 手がかり 30 | **8〜9 μs** | **5.5〜6.6 μs** |
| 手がかり 23 | **81〜84 μs** | **764〜864 μs** |
| 手がかり 17 A | 22〜26 μs | 21 μs |
| 手がかり 17 B | 17〜19 μs | 17 μs |
| 空の盤面 | 239〜251 μs | — |
| 敵対的な盤面(複数解) | — | **約 2.2 秒** |

## 考察

### 一意解の判定は穴あけの律速にならない

**現実的な問題では 1 回あたり数十〜数百 μs である。**
穴あけは 81 回程度 `countSolutions` を呼ぶので、**1 問あたり数 ms〜100 ms 程度**に収まる見込み。
C++ 実装の公開値(最難クラスで 100 μs 未満)と比べても**同じ桁か 1 桁落ち**であり、
「JavaScript 版は非常に遅い」という警告ほどの差は出なかった。

**制約伝播(Naked Single / Hidden Single)を分岐の前に尽くしていることが効いている。**
手がかり 17 個の問題が 30 個の問題と同じ桁で解けているのは、
手がかり数ではなく**伝播で決まるマスの多さ**が効くためである。
これは[「手がかり数は難易度の指標にならない」](../algorithms/difficulty-rating.md#-手がかり数で難易度を決めてはいけない)
という事実と同じ方向を向いている。

### 「一意であることの証明」は「1 つ解くこと」より高くつく

**手がかり 23 の盤面では 10 倍の差が出た**(84 μs → 864 μs)。
解を 1 つ見つけるのは早いが、**2 つ目が無いことを示すには探索木を最後まで見る**必要があるためである。

**⇒ 遊技側の答え合わせに `countSolutions` を使わない。**
答えはパックに入っている([問題ファイルの形式](../api/puzzle-file-format.md))ので解き直す必要が無い。

### 敵対的な盤面では 2 秒かかる

手がかりが左上に偏り、伝播がほとんど効かない盤面では**約 2.2 秒**かかった。
**この形は生成では踏まない。** 穴あけは完成盤から手がかりを減らしていくので、
評価する盤面は常に「解が少なくとも 1 つある」ものである。

**ただし外から来た盤面(遊技者が作った問題・取り込んだデータ)には上限が要る。**
現状の `countSolutions` に時間の上限は無い。実装するときは
[保留中の判断事項](../reference/pending-decisions.md) へ上げる。

## 結論

- **一意解の判定は生成のボトルネックにならない。** 設計どおり進めてよい
- **TypeScript でも実用速度が出る。** 公開値の警告を理由に実装方針を変える必要は無い
- **穴あけと難易度評価を実装したら、1 問あたりの生成時間を測り直す**
  ([未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 3 はまだ閉じない)

## 残課題

| # | 内容 |
|---|------|
| 1 | **生成 1 問あたりの所要時間は未測定。** 穴あけと難易度評価を実装してから測る |
