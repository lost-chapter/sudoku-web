# 検証: 問題の生成の所要時間と手がかり数の分布(TypeScript)

## 目的

**生成 1 問あたりの所要時間を実測する**
([未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 3)。

同時に**手がかり数の分布**を記録する。
[盤面の生成](../algorithms/board-generation.md#-手がかりを減らしても難しくならない) が
「一様ランダムに極小問題を取ると 24〜25 手がかり付近が圧倒的多数」と書いているので、
**実装がその形になっているかを確かめる**のが目的である
(なっていなければ、穴あけか一意解の判定が壊れている)。

⚠️ **難易度の評価はまだ実装していない。** ここで測ったのは
**完成盤の生成 + 穴あけまで**であり、
「目標クラスに外れた問題を捨てる」分は含まれていない。

### 完成盤の生成(穴あけを含まない)

| 項目 | 値 |
|------|-----|
| 1 個あたり | **105.5 μs** |
| 毎秒 | 約 9,500 個 |
| やり直し | **10,000 個で 0 回**(上段バンドと第 1 列の埋め方は必ず完成盤へ延ばせた) |

### 問題の生成(完成盤 + 穴あけ)

| 項目 | 値 |
|------|-----|
| 1 問あたり | **1.56 ms** |
| 毎秒 | **約 640 問** |
| 一意解 | 抜き取り 100 問すべて(100 / 100) |

**穴あけが全体の約 93% を占める**(1.56 ms のうち完成盤の生成は 0.11 ms)。
穴あけは 1 マス消すごとに `countSolutions` を呼ぶので、
81 回前後の一意解判定がそのまま時間になる。

## 考察

### 生成の速度は問題にならない

**単スレッドで毎秒 640 問。** 同梱パックの想定が 1 クラス 1,000 問なので、
**1 クラスあたり約 1.6 秒**で作れる。

参考(いずれも公開値。**C++ / Java であり、難易度評価を含む**)。

| 実装 | 値 |
|------|-----|
| QQwing(標準版) | 40 問/秒 |
| QQwing(Java 版) | 1,000 問/秒 |
| 本実装(TypeScript・単スレッド・**難易度評価なし**) | 640 問/秒 |

⚠️ **この比較を「同等の性能が出た」と読まない。** 難易度評価を入れると、
**目標クラスに外れた問題を捨てる分だけ実効の生成速度が落ちる**。
捨てる割合は工程 2 の 5 で実測する。

### 分布は調査どおりだった

**中央値 24・平均 24.37 で、24〜25 に山がある。**
これは調査の「一様ランダムに極小問題を取ると 24〜25 手がかり付近が圧倒的多数」と一致する。

**17 手がかりの問題は 1,000 問で 1 つも出なかった**(最小 21)。
既知の 17 手がかり問題が 49,158 件しか無いことを考えれば当然であり、
**手がかり数を狙って減らす作りにしていないことの裏付け**にもなる。

### 極小性は「要件にするか」ではなく「既定で付いてくる」

[未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 4 は
「極小性を要件にするか(生成コストを測ってから判断)」だった。

**いまの穴あけは、消せる位置が尽きるまで消すので必ず極小になる。**
極小をやめても速くはならない(**途中で止める判断のほうが余計**)。
**⇒ 極小性は要件として据えてよい。**

## 結論

- **生成 1 問あたり 1.56 ms(単スレッド)。パック 1,000 問で約 1.6 秒**
- **手がかり数の分布は調査どおり**(24〜25 に山)。実装が想定どおりの形になっている
- **極小性は既定で得られる**ので要件にしてよい([未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 4 を閉じられる)
- **難易度評価を入れたら測り直す。** 捨てる分で実効速度が変わる
