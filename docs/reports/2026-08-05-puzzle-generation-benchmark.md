# 検証: 問題の生成の所要時間と手がかり数の分布(TypeScript)

## 目的

**生成 1 問あたりの所要時間を実測する**
([未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 3)。

同時に**手がかり数の分布**を記録する。
[盤面の生成](../algorithms/board-generation.md#-手がかりを減らしても難しくならない) が
「一様ランダムに極小問題を取ると 24〜25 手がかり付近が圧倒的多数」と書いているので、
**実装がその形になっているかを確かめる**のが目的である
(なっていなければ、穴あけか一意解の判定が壊れている)。

⚠️ **難易度の評価はまだ実装していない。** ここで測ったのは
**完成盤の生成 + 穴あけまで**であり、
「目標クラスに外れた問題を捨てる」分は含まれていない。

**この文書の値は「`node` で実行したとき」のものである。**

## 結果

### 完成盤の生成(穴あけを含まない)

| 項目 | 値 |
|------|-----|
| 1 個あたり | **105.5 μs** |
| 毎秒 | 約 9,500 個 |
| やり直し | **10,000 個で 0 回**(上段バンドと第 1 列の埋め方は必ず完成盤へ延ばせた) |

### 問題の生成(完成盤 + 穴あけ)

| 項目 | 値 |
|------|-----|
| 1 問あたり | **1.56 ms** |
| 毎秒 | **約 640 問** |
| 一意解 | 抜き取り 100 問すべて(100 / 100) |

**穴あけが全体の約 93% を占める**(1.56 ms のうち完成盤の生成は 0.11 ms)。
穴あけは 1 マス消すごとに `countSolutions` を呼ぶので、
81 回前後の一意解判定がそのまま時間になる。

## ⚠️ 実行環境で数値が 5〜7 倍変わる(2026-08-05 追記)

**この報告の 1.56 ms/問 が、管理役(agent-a)の手元で再現しなかった**
(7.67 ms/問)。**原因を切り分けたので記録する。**

### 同じ機械・同じ負荷・同じコードで測り直した

`load average` 12.2〜12.6 の同一条件、300 問 × 2 回。

| 実行のしかた | 完成盤 | 問題(完成盤 + 穴あけ) |
|-------------|--------|---------------------|
| **`node` で直接** | 108〜111 μs | **1.52〜1.59 ms** |
| **Vitest 上**(module を分けたまま) | 521〜544 μs | **7.66〜7.88 ms** |
| **Vitest 上(`core` を 1 ファイルに束ねて)** | 78〜101 μs | **1.09〜1.13 ms** |

**agent-a が測った 7.67 ms/問・525 μs/個は、Vitest 上の値としてぴたりと再現した。**

### 原因は負荷ではなく module の分け方だった

**3 行目が決定的である。** Vitest のままでも、`core` を 1 ファイルに束ねると
**7.88 ms → 1.13 ms** になった。負荷も機械もコードも同じで、変えたのは
**module をまたぐかどうかだけ**である。

Vitest(vite-node)は module をまたぐ呼び出しを
**名前空間オブジェクトのプロパティ参照へ書き換える**。
`candidateMaskAt` や `place` のような**内側のループで何万回も呼ぶ関数**が
その形になると、最適化(インライン展開)が効かなくなる。

**⇒ 素の速さではなく「module 境界をまたぐ呼び出しの遅さ」を測っていた。**

### どの数値を信じるか

| 用途 | 見るべき値 |
|------|-----------|
| **生成器の実効速度**(`generator` は Node で動く) | **`node` の値**(1.5 ms/問) |
| **遊技側の体感**(本番ビルドは Vite が束ねる) | **束ねた値**(1.1 ms/問) |
| Vitest 上の値 | **製品の性能として引用しない** |

**⇒ 本文の結論は変わらない。** ただし**測り方を書かずに数値を出すと再現できない**。
[テストの方針](../verification/testing-policy.md) の「性能を測るときの約束」に手順を残した。

## 考察

### 生成の速度は問題にならない

**単スレッドで毎秒 640 問。** 同梱パックの想定が 1 クラス 1,000 問なので、
**1 クラスあたり約 1.6 秒**で作れる。

参考(いずれも公開値。**C++ / Java であり、難易度評価を含む**)。

| 実装 | 値 |
|------|-----|
| QQwing(標準版) | 40 問/秒 |
| QQwing(Java 版) | 1,000 問/秒 |
| 本実装(TypeScript・単スレッド・**難易度評価なし**) | 640 問/秒 |

⚠️ **この比較を「同等の性能が出た」と読まない。** 難易度評価を入れると、
**目標クラスに外れた問題を捨てる分だけ実効の生成速度が落ちる**。
捨てる割合は工程 2 の 5 で実測する。

### 分布は調査どおりだった

**中央値 24・平均 24.37 で、24〜25 に山がある。**
これは調査の「一様ランダムに極小問題を取ると 24〜25 手がかり付近が圧倒的多数」と一致する。

**17 手がかりの問題は 1,000 問で 1 つも出なかった**(最小 21)。
既知の 17 手がかり問題が 49,158 件しか無いことを考えれば当然であり、
**手がかり数を狙って減らす作りにしていないことの裏付け**にもなる。

### 極小性は「要件にするか」ではなく「既定で付いてくる」

[未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 4 は
「極小性を要件にするか(生成コストを測ってから判断)」だった。

**いまの穴あけは、消せる位置が尽きるまで消すので必ず極小になる。**
極小をやめても速くはならない(**途中で止める判断のほうが余計**)。
**⇒ 極小性は要件として据えてよい。**

## 結論

- **生成 1 問あたり 1.56 ms(単スレッド)。パック 1,000 問で約 1.6 秒**
- **手がかり数の分布は調査どおり**(24〜25 に山)。実装が想定どおりの形になっている
- **極小性は既定で得られる**ので要件にしてよい([未解決の課題](../guides/implementation-roadmap.md#未解決の課題全体) の 4 を閉じられる)
- **難易度評価を入れたら測り直す。** 捨てる分で実効速度が変わる

## ⚠️ 追記(2026-08-05・管理役): 負荷という見立ては誤りだった

**最初この差を「実行環境の負荷」と書いたが、それは誤りである**(agent-b の切り分けで判明)。
**主因は実行のしかた**で、負荷ではない。

| 測り方 | 問題の生成 | 完成盤のみ | 誰が測ったか |
|--------|-----------|-----------|------------|
| `node` で直接 | **1.5 ms/問** | 105〜111 μs/個 | agent-b |
| Vitest 上 | **7.7〜7.9 ms/問** | 521〜544 μs/個 | 両方(一致) |
| Vitest 上 + `core` を 1 ファイルに束ねる | **1.1 ms/問** | 78〜101 μs/個 | agent-b |
| tsx 上 | **15.3 ms/問** | 1,031 μs/個 | 管理役 |

**同じ機械・同じ負荷(`load average` 12 前後)で、変えたのは束ねるかどうかだけ**という
対照実験で切り分けられている。機序と今後の測り方は
[テストの方針](../verification/testing-policy.md#性能を測るときの約束)。

### 管理役が確かめられたこと / 確かめられなかったこと

**確かめられた。**

- Vitest 上 **7.67 ms/問**(agent-b の 7.66〜7.88 と一致)
- tsx 上 **15.3 ms/問**(`load average` 12.3)
- **乱数の与え方は関係ない**(共有の乱数 / 1 問ごとの新シード / 毎回同じシードで差なし)

⚠️ **確かめられなかった: `node` で直接の 1.5 ms。**
`packages/core` のソースは**拡張子なしの相対 import** を使っており、
束ねずに `node` へ直接食わせると `ERR_MODULE_NOT_FOUND` になる。
**このため管理役の側では node 直接の経路を再現できていない。**

### ⚠️ 実務上いちばん効くこと —— 生成器は今 tsx で動く

`packages/generator` の実行は **`tsx src/cli.ts`**、つまり**上表でいちばん遅い経路**である。

**⇒ いまのままパックを作ると 1 問あたり 15 ms 前後になる**(1,000 問で約 15 秒)。
実用上は困らないが、**「1.5 ms/問」を生成器の実効速度として引用してはいけない。**
工程 2 の 6 で大量生成を回すときは、束ねて実行するか、実測して記録すること。
