# フリック操作の検討(2026-08-06)

**発注者の要望「スマホ画面ではフリックを使った操作の導入を検討してみてください」に対する調査。**

⚠️ **採否は発注者が決める。この文書は判断材料であって、決定ではない。**

## 結論(先に)

**4 案のうち A(数字キーの上フリックでメモ)だけを試作した。**
**B・C・D は、試作する前に採らない理由が見つかった。**

| 案 | 中身 | 判定 |
|----|------|------|
| **A** | **数字キーを上へはじくとメモ、タップで確定入力** | 🎯 **試作した。動いている** |
| B | 盤面を左右へスワイプして取り消し / やり直し | ❌ **画面端の OS ジェスチャと重なる** |
| C | セルを長押し → 放射状メニューで数字を選ぶ | ❌ **9 方向は指の精度に対して多すぎる** |
| D | 盤面をスワイプして選択セルを動かす | ❌ **B と同じ問題があり、得るものが小さい** |

## 判断の土台になった実測(375×812)

| 何を | 値 |
|------|-----|
| 盤面の**左端 / 右端から画面の端まで** | 🔴 **4px** |
| 数字キー(下段)の**下端から画面の下まで** | **64px** |
| 数字キー(上段)の同上 | 120px |
| 「メモ」キーの同上 | 8px |
| 盤面とキーの `touch-action` | `manipulation`(既存) |

🎯 **盤面は画面の端に張り付いている。入力パッドは下端から離れている。**
**この 1 つの事実が、A を残して B・D を落とした。**

## 4 案の比較

| | A(採用) | B | C | D |
|---|---------|---|---|---|
| 何が良くなるか | **メモの切替が要らない** | 補助行のボタンが減る | パッドが要らず盤面が大きい | 小さいセルを突かなくてよい |
| 既存の操作 | **消さない**(追加の経路) | 消さない | ⚠️ **パッドを外すなら消える** | 消さない |
| **OS ジェスチャ** | ✅ **下端から 64px 離れている** | 🔴 **左右端から 4px** | ⚠️ 長押しは OS の選択と競合 | 🔴 **B と同じ** |
| 縦横の両立 | ✅ **同じ部品なので両方で効く** | ✅ | ⚠️ **横向きは盤面が左端に寄る** | ✅ |
| 誤爆したら | **候補が 1 つ立つ。取り消しで戻る** | ⚠️ **盤面の選択が飛ぶ** | ⚠️ **意図しない数字が入る** | **選択が動くだけ** |
| 実装の重さ | **小**(60 行) | 中 | 🔴 **大**(重ね表示・当たり判定・読み上げ) | 小 |

### なぜ B と D を落としたか

**盤面は画面の左右の端から 4px しかない。**
**iOS も Android も、画面の端からのスワイプを OS が取る**(戻る・通知・切替)。
⚠️ **盤面の端を掴んだスワイプは、アプリまで届かないか、OS の動作と二重に起きる。**

**盤面に余白を足せば避けられるが、それは盤面を小さくすることである。**
[ADR 0005](../decisions/0005-mobile-dedicated-layout.md) で
**盤面の大きさを最優先すると決めているので、逆行する。**

⚠️ **B の得るもの(補助行のボタンが減る)は、盤面を削ってまで取るものではない。**
**取り消しはボタンで足りている。**

### なぜ C を落としたか

**盤面が大きくなるのは魅力的だが、9 個を放射状に置くのは指の精度に合わない。**
**1 方向あたり 40°しかなく**、**1 セル 40.1px の盤面の上で 40° を撃ち分けることになる。**

**3×3 のポップアップにすれば精度は足りるが、**
⚠️ **盤面の上に重なるので「いまどのセルへ入れているのか」が見えなくなる。**
**数独は周りのマスを見ながら数字を決める遊技なので、これは中身に触る変更である。**

**加えて、長押しは OS の文字選択・コンテキストメニューと競合する。**

## 試作した A の中身

```
タップ(そのまま離す)     → 確定入力(いままでどおり)
上へ 24px 以上はじく      → その 1 回だけメモ
```

⚠️ **メモモードのキーは残してある。** **フリックは追加の経路であって、置き換えではない。**
**キーボードだけで遊べること**(工程 4 の完了条件)**も変わらない。**

| 置き場所 | 中身 |
|---------|------|
| `state/boardState.ts` | `inputDigit` に `asNote?: boolean` を足した。**その 1 回だけメモにする。モードは動かさない** |
| `features/input/useFlick.ts` | 上フリックの判定(**新規・60 行**) |
| `features/input/TouchPad.tsx` | 数字キーを `DigitKey` に切り出し(`map` の中では hook を呼べないため) |

### 決めた閾値と、その理由

| 値 | 理由 |
|----|------|
| **上へ 24px 以上** | ⚠️ **キーの高さ(48px)の半分**。キーの中で完結する動きはタップ、**キーから出ていく動きはフリック**、という分け方である。🔴 **当初は「手ぶれと区別が付く必要がある」を根拠にしていたが、その仕事はブラウザの slop が先にやっていた**(下記) |
| **縦 > 横** | ⚠️ **斜めを上フリックにすると、隣のキーへ滑らせただけで候補が立つ** |
| **時間の制限なし** | ゆっくり上げても意図は同じ。**速さを条件にすると、慣れていない人ほど失敗する** |

### 🔴 `touchend` で必ず `click` を止め、タップも自分で発火する

**止めないと、メモを立てたあとに確定入力まで入る。**
React は `touchend` を passive にしないので `preventDefault()` が効く
(`touchstart` は passive なので、そちらでは止められない)。

⚠️ **フリックのときだけ止めるのでは足りない。**
**タップかどうかの判定をブラウザに任せると、slop の分だけ穴が開く。**
**⇒ 指の操作は全部こちらで振り分ける**(タップ / フリック / 取り消し)。
**マウスとキーボードは `onClick` のまま** —— そちらに `touchend` は来ない。

## 実測(ブラウザ面・375×812 と 568×320)

**合成した `TouchEvent` を送り、選択セルの読み上げラベルで結果を見た。**

🔴 **この節の最初の表は誤っていた。2026-08-06 に書き直した。**
**下の「合成した `TouchEvent` では分からない」を参照。**

**CDP で本物のタッチを送った結果**(`packages/web/e2e/flick.e2e.ts`)。

| 上への移動 | 結果 |
|-----------|------|
| 0 / 10 / 14 / 16 / 20 / 23px | **確定入力** |
| **24px 以上**(24 / 30 / 40) | **候補** |
| キーの外で離す | **何も起きない**(取り消し) |

| その他 | 結果 |
|--------|------|
| **横向き(568×320)で上へ 30px** | **候補が立つ**(同じ部品なので両方で効く) |
| メモモードの状態 | **切のまま**(モードを動かさない) |

### 🔴 合成した `TouchEvent` では分からない(2026-08-06 に判明)

**最初の実測は、JS から `TouchEvent` を組み立てて送り、
`preventDefault` されなければ自分で `click` を出す、という形だった。**

⚠️ **その「自分で `click` を出す」がブラウザの挙動を消していた。**
**実際のブラウザは、指が少し滑ると `click` の合成をやめる**(tap slop。実測でおよそ 15px)。

**⇒ 閾値を 24px にしていた間、15〜24px は「何も起きない」領域だった。**
**私の測り方ではそれが「確定入力」に見えていた。**

🎯 **合成したイベントは、人の操作を代表していない。**
**`click` が来るかどうかまで自分で決めてしまうと、そこは測れていない。**

**⇒ 直し方は「閾値を下げる」ではなく「`click` に任せるのをやめる」を採った。**
**slop の値はブラウザと端末で変わるので、閾値を下げても穴の位置が動くだけである。**

| 検査 | 結果 |
|------|------|
| 単体テスト | **118 件**(114 → +4。`asNote` の 4 件) |
| E2E | **38 件・19.1 秒**(増減なし。**既存の操作を壊していない**) |
| バンドル(gzip) | 107.54 → **107.76 KB(+0.22 KB)** |

## 🔴 実機でしか確かめられないこと

⚠️ **ブラウザ面には OS のジェスチャが無い。** 下の 3 つは**実機で触るまで分からない。**

| # | 確かめること | いまの見立て(**根拠は実測と一般論の組み合わせ**) |
|---|------------|------------------------------|
| 1 | **iOS のホームバーと競合しないか** | **数字キーは下端から 64px 離れている**ので、当たらないと見込む。⚠️ **バーの反応領域を実機で測っていない** |
| 2 | **指の実際の動きが 24px を超えるか** | 合成イベントでは「意図した動き」しか送れない。⚠️ **人が「はじく」ときの実際の距離を測っていない**。短すぎれば確定入力になり、**気づかないまま数字が入る** |
| 3 | **フリックが「発見される」か** | ⚠️ **画面のどこにも「上へはじける」と書いていない**。知らない人には無い機能と同じである |

🎯 **3 が採否の分かれ目だと考える。**
**A の価値は「メモの切替が要らない」ことだが、知らなければ切替を使い続けるだけで、損はしない。**
**⇒ 入れても害が無く、気づいた人だけが速くなる、という性質の機能である。**

## 採るとき / 採らないとき

**採るなら決めること。**

1. **どう気づかせるか。** 初回に短い案内を出すか、設定に説明を置くか、何もしないか
   (⚠️ **何もしない**でも成り立つ。**上の 3 のとおり、知らない人は損をしない**)
2. **下フリックに何かを割り当てるか。** ⚠️ **いまは空けてある。**
   「消す」を割り当てる案があるが、**誤爆したときに入力が消えるので慎重に**
3. **読み上げでどう案内するか。** ⚠️ **いまは案内していない。**
   **フリックは読み上げでは使えない操作**なので、名前に混ぜると**その経路を持たない人へ届かない案内になる**

**採らないなら戻すもの。**

- `features/input/useFlick.ts`(削除)
- `TouchPad.tsx` の `DigitKey` から `useFlickUp` を外す
- ⚠️ **`asNote` は残してよい**。モードに依らずメモを入れる口は、
  **フリック以外の入り口(例: 長押し・キーの組み合わせ)でも使える**
