# システム構成

**この構成は「問題を作る側」と「問題を遊ぶ側」を分けることを軸にしている。**
[プロジェクトの目的](../overview/project-purpose.md) の要件 4(外部ファイル化)と
5(大量生成)から導かれた形である。

## 全体像

```
                 [ 作る側 / Node ]                     [ 遊ぶ側 / ブラウザ ]

  packages/generator  ──生成──▶  puzzles/  ──fetch──▶  packages/web
        │                       (問題パック)                  │
        └────────┐                                      ┌─────┘
                 ▼                                      ▼
                        packages/core(盤面ロジック)
                     生成・解法・検証・難易度評価を両側で共有
```

**`packages/core` を両側から使うことが構成の要である。**
遊技側で「入力が正しいか」を判定するロジックと、生成側で「一意解か」を判定するロジックは
同じソルバである。二重に実装すると、生成した問題を遊技側が矛盾と判定する事故が起きる。

## パッケージ構成

pnpm workspaces のモノレポ([ADR 0001](../decisions/0001-project-structure.md))。

```
sudoku-web/
├── packages/
│   ├── core/          盤面ロジック。DOM も Node API も使わない
│   ├── generator/     問題を大量生成する CLI(Node)
│   └── web/           React + TypeScript のアプリ
├── puzzles/           生成された問題パック(配信物)
├── tools/
│   └── docs-html/     Markdown → HTML(docs-markdown-to-html スキル)
└── docs/
```

| パッケージ | 責務 | 依存してよいもの |
|-----------|------|----------------|
| `core` | 盤面の表現・検証・ソルバ・完成盤の生成・穴あけ・難易度評価・問題ファイルの読み書き | **何にも依存しない** |
| `generator` | 大量生成の CLI・並列実行・パックの書き出し・マニフェストの生成 | `core` と Node の標準 API |
| `web` | 画面・操作・状態管理・進行の保存・問題の取得 | `core` と UI ライブラリ |

**依存の向きは一方通行である。** `core` は `web` も `generator` も知らない。

### `core` が守る 3 つの制約

1. **DOM と Node API を使わない。** ブラウザでも Node でも同じコードが動くこと
2. **乱数を内部で作らない。** 乱数は**シードを受け取る関数として外から注入する**。
   同じシードからは同じ問題ができる(生成の再現性は
   [盤面の生成](../algorithms/board-generation.md) の要)
3. **副作用を持たない。** ファイルも読まず書かない。入出力は呼び出し側の責務

**この 3 つが崩れると、生成のテストが書けなくなる。**

## データの流れ

### 1. 生成(オフライン・バッチ)

```
シード ──▶ 完成盤の生成 ──▶ 穴あけ(一意解を保つ) ──▶ 難易度評価 ──▶ パックへ追記
```

`generator` が `worker_threads` で並列に回す。
1 問ごとに独立しているので、**並列化の効きが素直**である。
詳細は [盤面の生成](../algorithms/board-generation.md)。

### 2. 配信

`puzzles/` のパックを `web` のビルド成果物へ含め、静的ファイルとして配る。
アプリは**必要なパックだけを実行時に `fetch` する**(全部を最初に読み込まない)。
形式と分割の方針は [問題ファイルの形式](../api/puzzle-file-format.md)。

### 3. 遊技

```
難易度を選ぶ ──▶ マニフェストを見る ──▶ 該当パックを fetch ──▶ 1 問取り出す
      ──▶ 盤面の状態を reducer で進める ──▶ localStorage へ保存
```

## `web` の内部構成

```
packages/web/src/
├── app/           画面(ルーティング・レイアウト)
├── features/
│   ├── board/     盤面の描画とセルの操作
│   ├── input/     数字入力・メモ・取り消し
│   ├── puzzle/    問題の取得(マニフェスト・パックの読み込み)
│   └── progress/  進行の保存と復元
├── state/         盤面の状態管理(core の reducer を React へつなぐ)
└── ui/            UI ライブラリのラッパと共通部品
```

### 状態管理は reducer に寄せる

**盤面の状態遷移は `core` 側の純粋な reducer として書く。**
React には `useReducer` でつなぐだけにする。

```
(state, action) => state      ← core。React を知らない
```

**理由は 2 つ。**

- **取り消し(undo)が自然に書ける。** action を積めば履歴になる
- **盤面の振る舞いを React 抜きでテストできる。** 描画のテストと分離できる

**UI ライブラリの選定は [ADR 0002](../decisions/0002-ui-library-selection.md)。**
盤面(9×9 のグリッド・セル選択・候補の表示)は**どのライブラリにも無いので自前で作る**。
ライブラリに任せるのは盤面の外側(ボタン・モーダル・選択・通知・テーマ)である。

## 進行の保存

| 保存するもの | 場所 | 形式 |
|-------------|------|------|
| 遊びかけの盤面(入力・メモ・経過時間) | `localStorage` | 問題 ID + 差分 |
| 設定(テーマ・メモの表示・自動チェック) | `localStorage` | 設定オブジェクト |

**盤面そのものを丸ごと保存しない。** 問題 ID と「遊技者が入れた分」だけを持てば復元できる
(手がかりはパックから引き直せる)。契約は
[問題ファイルの形式](../api/puzzle-file-format.md) と揃える。

## エラーハンドリングの方針

| 起きること | 扱い |
|-----------|------|
| パックの取得に失敗する | 遊技を止めない。**取得済みの問題があればそれを出す**。無ければ再試行を促す |
| パックの中身が壊れている | **読み込み時に検証して弾く**(81 文字・使える文字・一意解のメタが揃っているか) |
| 保存した進行が復元できない | 黙って捨てて新しい盤面から始める。**保存の失敗で遊べなくならないこと** |
| 遊技者の入力が数独の規則に反する | エラーではない。**矛盾として表示するだけ**(消せる) |

**遊技を止めてよいのは「問題が 1 問も無いとき」だけ。**
