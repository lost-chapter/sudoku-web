# 0003 問題を事前生成した外部ファイルとして持つ

## ステータス

採用(2026-08-05)

## 背景

要件は「**問題を外部ファイル化すること**」と「**問題は大量に生成できること**」
([プロジェクトの目的](../overview/project-purpose.md) の 4 と 5)。

問題の供給方法には 3 通りある。

| 方法 | 中身 |
|------|------|
| A. 実行時生成 | ブラウザで遊ぶたびに生成する |
| B. サーバ配信 | サーバが生成・保管し、API で配る |
| C. **事前生成 + 静的ファイル** | オフラインで大量に作っておき、ファイルとして配る |

一意解を保つ穴あけと難易度の評価は**ソルバを何度も回す処理**である。
これを遊技のたびに走らせると、端末の性能差がそのまま待ち時間になる。

## 決定内容

**C を採用する。問題は事前に生成し、静的ファイルとして配信する。**

- 生成は `packages/generator` の CLI が **Node で** 行う
- 出力は `puzzles/` 配下の**パックファイル**とマニフェスト
  ([問題ファイルの形式](../api/puzzle-file-format.md))
- アプリは**必要なパックだけを実行時に `fetch`** する
- **サーバは持たない。** 静的ホスティングで配信する

**リポジトリに置くのは同梱パックだけとする。**

| 対象 | 置き場所 | Git |
|------|---------|-----|
| 同梱パック(各難易度の既定数。クローンしてすぐ遊べる分) | `puzzles/packs/` | **管理下** |
| 大量生成した追加分 | `puzzles/generated/` | **管理外**(`.gitignore`) |
| 生成の条件(シード・件数・生成器のバージョン) | マニフェスト | **管理下** |

**シードを記録するので、管理外の分はいつでも同じものを作り直せる。**
これが成り立つのは `core` が乱数を外から注入される設計だからである
([システム構成](../architecture/system-architecture.md) の「`core` が守る 3 つの制約」)。

## 判断理由

- **遊技側の待ち時間が端末性能に左右されない。** 重い処理は生成時に済んでいる
- **一意解と難易度を生成時に検証できる。** 収録前に落とせるので、
  遊技側は「壊れた問題」を考えなくてよい
- **サーバが要らない。** 静的ホスティングで完結し、運用コストがゼロに近い
- **問題の追加がコードの変更にならない。** ファイルを差し替えるだけで増やせる
- **リポジトリが肥大しない。** 同梱分だけをコミットし、残りはシードから再生成する

## 採用しなかった選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| A. 実行時生成 | 難易度を保証するには何度もソルバを回す必要があり、端末によって待たされる。要件 4(外部ファイル化)にも反する |
| B. サーバ配信 | 運用が要る。この規模で持つ利得が無い(記録もランキングも作らない) |
| 生成した問題を全部コミットする | 大量生成が要件なので、増えるほどリポジトリが重くなる。シードから再生成できるため保持する必要が無い |
| 問題を TypeScript の配列としてコードに埋め込む | 要件 4 に反する。ビルドが問題数に比例して重くなる |

## 影響

- **`puzzles/generated/` を `.gitignore` へ追加する**(工程 1)
- **マニフェストにシードと生成器のバージョンを必ず記録する。**
  無いと再生成できず、この決定の前提が崩れる
- **同梱パックの件数は決めていない**(難易度ごとに何問持つか)。
  工程 2 で実測(ファイルサイズと生成時間)してから決める
- 将来サーバを持つことにしたら、この ADR を「置き換え」として再検討する。
  そのときも**ファイル形式は契約として残せる**(配信元が変わるだけ)
