# 0005 スマートフォンは専用レイアウトにする

## ステータス

採用(2026-08-06)。**分岐の方法と部品の分け方は確定。⚠️ 寸法と横向きは実測待ち**

## 背景

発注者から **「スマートフォンで操作のしやすい UI を優先」** という要望が届いた。
**「UA などでがっつりコンポーネントを変えてもよい」** とも明言されている。

これまでは 1 つのレイアウトを幅で伸縮させていた
([端末ごとの作り](../ui/screens-and-interactions.md#端末ごとの作り))。**その前提が変わった。**

数独は**画面のほぼ全部を盤面が占める**遊技である。
9×9 のセルは狭い画面ほど窮屈になり、**入力パッドと盤面が縦に並ぶと 1 画面に収まらない。**
実測(幅 375px)ではセルが 38.8px、パッドを含めると縦スクロールが出る。

## 決定内容

**スマートフォンには専用のレイアウトを持つ。** 幅の調整では足りないと判断する。

| 端末 | 作り |
|------|------|
| スマートフォン(縦) | **画面いっぱいに盤面、下部に固定した大きな入力パッド。スクロールしない 1 画面** |
| それ以外 | いまのレイアウト(中央寄せ・縦に積む) |

**判定は UA だけに頼らない。** ⚠️ **UA は偽装も変更もされる。**
どちらへ転んでも遊べることを条件とし、**判定を外したときに起きることを
「遊べない」ではなく「見た目が好みでない」に留める。**

## 判断理由

- **数独は 1 画面で完結すべき遊技である**。盤面とパッドを行き来するのに
  スクロールが要ると、指の移動と視線の移動が毎手発生する
- **片手で遊べることに価値がある**。パッドを下部に固定すれば親指の可動域に入る
- **レスポンシブの延長では、盤面を最大化しながらパッドを大きくできない。**
  同じ縦方向の領域を奪い合うため、**どちらかが必ず小さくなる**
- **ユーザーが分岐を明示的に許可している**。維持の手間より操作性を優先すると決まっている

## 採用しなかった選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| いまのレイアウトの余白と大きさを詰める | 盤面とパッドが縦を奪い合う構造は変わらない。**1 画面に収まらない** |
| 盤面を縮めてパッドを大きくする | 盤面のセルは幅 375px で **38.8px が上限**。これ以上小さくすると WCAG 2.2 の 24px に近づく |
| ネイティブアプリにする | 要件は Web アプリ([プロジェクトの目的](../overview/project-purpose.md))。配信も未定 |
| UA だけで分岐する | ⚠️ **UA は偽装される**。外したときに遊べなくなる作りにしてはいけない |

## 分岐の方法(2026-08-06 確定)

### 🎯 UA では分岐しない

**判定は「幅 × 入力装置」で行う。**

```
狭い画面向けのレイアウト = (pointer: coarse) かつ (幅か高さが狭い)
```

⚠️ **`navigator.userAgent` を使わない。**
**iPadOS は既定で Mac を名乗り、デスクトップ表示に切り替えたスマートフォンも Mac を名乗る。**
UA で分けると「スマートフォンなのに PC 版」「PC なのにスマートフォン版」が**構造的に避けられない**。

`pointer: coarse` は**いま触っている入力装置の実際の性質**、幅は**いま使える領域**である。
どちらも**偽装する動機が無く、外れても実害が小さい**。

**ユーザーは「UA でがっつり変えてよい」と許可したが、これは手段の許可であって
UA を使えという指示ではない。** ⇒ **分ける度合いは大胆に、分ける手段は堅く。**

### 判定を外しても壊れない

**これが分岐を入れる条件である。**

| 誤判定 | 起きること | 遊べるか |
|--------|-----------|---------|
| スマートフォンを PC 版と判定 | 縦に長く、スクロールする | **遊べる**(従来の画面) |
| PC をスマートフォン版と判定 | 大きなボタンが下部に固定される | **遊べる**(キーボードも効く) |

**どちらのレイアウトも単独で完結した遊技可能な画面にする。**
**分岐は「より良いほうを出す」だけで、分岐の失敗が機能の喪失にならない。**

### ⚠️ 判定式の正本は 1 か所に置く

初回描画のちらつきを消すため `index.html` の先頭スクリプトでも判定するが、
**JS 側の `useMediaQuery` と条件が二重になる。**
**条件式の正本を 1 か所に置き、両方がそれを参照すること。**
**片方だけ直して食い違うのが、この手の仕組みでいちばん多い壊れ方である。**

## 確定した設計(2026-08-06)

| 項目 | 決めたこと |
|------|-----------|
| **`Board`** | **共有する**。DOM も props も変えず、**一辺の決め方だけ**を外から与える。色・区切り線・強調を分けると**コントラストの検査を 2 回やる羽目になる** |
| **入力パッド** | **分ける**(`TouchPad` を新設)。並び・固定位置・キーの大きさが別物。1 つの部品に条件分岐で押し込むと**片方だけ壊れる** |
| **状態・ホットキー・保存・完成判定** | **`Game` に残す。レイアウトは表示だけを持つ** |
| **あきらめるボタン** | **ヘッダの右**(親指からいちばん遠い)+ **確認モーダル**(既定のフォーカスは「やめる」)。**置き場所と確認の二重で防ぐ** |
| **キーボード操作** | `role="grid"` / Tab の対象は盤面 1 つ / ホットキーは 1 か所、を**両レイアウトで共有** |
| **E2E** | **既存の 3 件をスマートフォン幅でも回す**(テストは増えない)。⚠️ **加えて「縦スクロールしないこと」を 1 件足す** —— ユーザーの明示要件なのに、**どの検査も見ていなかった** |

🎯 **振る舞いは 1 つ、見た目は 2 つ。**
**分けてよいのは「並べ方と寸法」だけで、状態・意味づけ・キー操作を分けたら負けである。**

## 🔴 切り替えても遊技が続くこと(2026-08-06 に欠陥を出して追加)

**幅を広げただけで、入力も保存も消え、別の問題が出た。**

| 幅 | 入力 | 保存 | 問題 |
|----|------|------|------|
| 390×664(スマホ版) | 2 | 2 | `line 437` |
| → 1280×900(PC 版) | **0** | **null** | **`line null`** |

**外枠(タイトルと余白)を「有無」で切り替えていたのが原因である。**

```jsx
if (screen.name === "game" && phone) return <GameScreen … />;   // ← ここ
return <Container><Stack><Title/><GameScreen … /></Stack></Container>;
```

⚠️ **`GameScreen` の置き場所が変わると、React は同じ画面と見なせず作り直す。**
遊技の状態は `Game` の `useReducer` にあるので、**作り直した瞬間に消える。**
**さらに、空になった盤面が「空なら保存を消す」規約を踏み、`localStorage` まで消えた**
⇒ **リロードしても戻らない。**

**⇒ 外枠は「有無」ではなく「太さ」で切り替える。**
要素は常に同じ場所に置き、余白とタイトルの表示だけを変える。

🎯 **「分けてよいのは並べ方と寸法だけ」には、「要素の置き場所」も含まれる。**
**置き場所を分けた時点で、状態を分けたのと同じことになる。**

### ⚠️ 実機の回転では起きなかった

**縦横を入れ替えても `PHONE_QUERY` は真のままなので、外枠は外れたままである。**
**実測でも入力・保存・問題のすべてが残った。**

⇒ **影響は「PC でウィンドウを狭める」「タブレットで画面分割の幅を変える」に限られる。**
⚠️ **限られるだけで、直さない理由にはならない**(遊技と保存が消えるため)。

### 検査は「切り替えを跨ぐ」ものでないと効かない

⚠️ **E2E 33 件が通っていたのに見つからなかった。**
**project ごとに幅を固定して回しており、切り替えが 1 度も起きていなかった。**

**⇒ `layoutSwitch.e2e.ts` を足した**。見るのは 3 つ ——
**入力が残っている / 保存が残っている / 同じ問題である。**
⚠️ **「描画が壊れていない」では足りない。** 別の問題が出ても描画は正常に見える。

## 横向きは専用の並べ方を持つ(2026-08-06・実測で確定)

⚠️ **最初の設計案は横向きを落としていた。実測して 2 つの誤りが分かった。**

| 端末(横) | 幅×高さ | いまの画面 | 幅だけの判定 |
|---------|--------|-----------|------------|
| iPhone X 級 | 812×375 | **532px はみ出す** | ❌ 外れて PC 版へ |
| iPhone 12 級 | 750×340 | はみ出す | ✅ 当たるが**縦向けの並べ方** |
| iPhone SE 級 | 568×320 | **647px はみ出す** | ✅ 当たるが**縦向けの並べ方** |

🎯 **「幅が 767 を超えるから落ちる」だけではなかった。**
**当たった先の並べ方が縦積みなので、当たっても収まらない。**
⇒ **条件式を直すだけでは足りず、横向き専用の並べ方が要る。**

```
狭い画面向け = (pointer: coarse) かつ (max-width: 767px または max-height: 500px)
横に並べる   = 上に加えて (orientation: landscape)
```

**`max-height: 500px` は 812×375 を拾うために足した。**
⚠️ **500 の根拠は「横向きの実測 3 種が 320〜375、縦向きは 568 以上。その間」だけである。**
**キリのよさ以上の意味は無い**(動かすときに迷わないよう明記する)。

**横向きは縦向きより余裕がある**(高さで頭打ちにならず、余った横幅にパッドを置ける)。
実測での 1 セルは 33.2〜39.4px。**⇒ 対応しない理由が無いので実装する。**

## スマートフォンは高さに関係なくスクロールさせない(2026-08-06・更新)

**スマートフォンではページと盤面領域のスクロールを発生させない。**
高さが足りない場合は盤面を残りの領域へ縮める。セル 24px の目安を下回る可能性はあるが、
**ユーザーの明示指定である「スマートフォンでは画面スクロールを一切発生させない」を優先する。**

画面全体に `overflow: hidden`、`overscroll-behavior: none`、`touch-action: none` を適用し、
盤面のスワイプ入力と文字選択の抑止も同じ境界で扱う。更新情報など、モーダル内部の読み物は
モーダル自身の領域でスクロールできる。

| # | 決めること | 状態 |
|---|-----------|------|
| 1 | `dvh` か `svh` か | **両方試して報告**。⚠️ **管理役は `svh` を推す** —— バーの出入りで盤面の大きさが変わるのは、同じマスを何度も見る遊技では気が散る |
| 2 | 初回描画のちらつきを消すか | **まず置かずに実装し、ちらつきを実測してから決める**。⚠️ **「二重管理を避けるため置かない」だけを理由にしない** —— 次の人が「ちらつく」と言って先頭スクリプトを足し、二重管理が復活する。**消すなら条件文字列をビルド時に注入する**(正本は 1 か所のまま) |
| 3 | あきらめて出した解の見せ方 | **細字・灰・網掛け + 「答え」のラベル**の方針は確定。⚠️ **網掛けの上の灰**という新しい重なりができるので、**幅 375px と 320px の両方で測り直す**。色は `--sudoku-color-revealed` に集める |

## ⚠️ E2E は実装をなぞらないこと

**「スクロールしない」の検査に、実装のしきい値を持ち込まない。**

```js
// ✅ この端末でどうなってほしいか、を固定する
test("390×664 では縦スクロールしない", ...)

// ❌ 実装を変えるとテストも一緒に動き、壊れても落ちない
if (height >= THRESHOLD) { expect(noScroll) } else { ... }
```

**しきい値を動かしたらテストが落ちる —— それが正しい姿である。**
⚠️ **「スクロールしてよい端末」の検査は要らない**。そこは要件ではなく妥協なので、固定する価値が無い。

  スマートフォン版で**触って遊べること**を機械で見るなら別の仕組みが要る。

  ⚠️ **増分を実測して記録すること**(削除後は JS 342.67 KB / gzip 105.76 KB)
