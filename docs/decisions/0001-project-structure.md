# 0001 プロジェクト構成を pnpm workspaces のモノレポにする

## ステータス

採用(2026-08-05)

## 背景

[プロジェクトの目的](../overview/project-purpose.md) の要件のうち、構成を決めるのは次の 2 つ。

- **問題を外部ファイル化する**(要件 4)
- **問題は大量に生成できる**(要件 5)

この 2 つから、**ブラウザで動くアプリとは別に、Node で動く生成バッチが必要**になる。
そして両者は**同じソルバ**を使う必要がある(生成側の「一意解の判定」と
遊技側の「入力の検証」は同じロジックである)。

つまり最低でも次の 3 つの実行単位が要る。

| 単位 | 実行環境 | 出力 |
|------|---------|------|
| 盤面ロジック | 両方 | ライブラリ |
| 生成バッチ | Node | 問題ファイル |
| アプリ | ブラウザ | 静的サイト |

## 決定内容

**pnpm workspaces のモノレポにし、3 パッケージへ分ける。**

```
packages/core       盤面ロジック(DOM も Node API も使わない)
packages/generator  生成 CLI(Node)
packages/web        React アプリ(ブラウザ)
```

技術構成は次のとおり。

| 項目 | 採用 | 理由 |
|------|------|------|
| 言語 | TypeScript | 要件 1。`strict` を有効にする |
| パッケージ管理 | pnpm workspaces | 依存の重複を持たず、パッケージ間参照が素直 |
| UI | React | 要件 1 |
| ビルド・開発サーバ | Vite | 開発サーバが速く、静的サイトの出力が既定。React + TS のテンプレートがある |
| テスト | Vitest | Vite と設定を共有できる。`core` の単体テストが主戦場 |
| Lint / 整形 | ESLint + Prettier | 並列作業時の差分ノイズを抑える |

**`core` は Node API も DOM も使わない。**
これは慣習ではなく**制約**で、破ると生成側と遊技側でロジックが割れる。

## 判断理由

- **ソルバを 1 つに保てる。** 別リポジトリに分けるとバージョン同期の手間が増え、
  同じリポジトリ内で 1 パッケージにまとめると `core` がブラウザ用の依存を抱え込む
- **問題ファイルが生成物としてリポジトリ内に置ける。**
  `generator` が `puzzles/` へ書き、`web` がそれを配信物として取り込む流れが 1 リポジトリで閉じる
- **並列作業の境界がパッケージ境界と一致する。**
  盤面ロジック / 生成 / UI は担当を分けやすい
  ([並列エージェントの運用](../guides/parallel-agent-operations.md))
- **Vite は静的サイトを出すだけで足りる。** サーバを持たない([ADR 0003](0003-external-puzzle-files.md))ので、
  SSR を持つフレームワークは要らない

## 採用しなかった選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| 単一パッケージ(`src/` 一式) | `core` がブラウザ向けの依存と設定に引きずられ、Node のバッチから使いにくくなる |
| Next.js | サーバを持たない構成では機能が過剰。静的出力だけのために設定が増える |
| npm / yarn workspaces | 動くが、pnpm のほうが依存の重複が無く、パッケージ間の参照が厳密 |
| Turborepo など | この規模ではタスクランナーを足す利得より設定の重さが勝つ |
| Jest | Vite と設定を二重に持つことになる |

## 影響

- **`core` の変更は両側に効く。** 変更時は生成側のテストと遊技側のテストを両方回す
- **`packages/` の追加は工程 1 で行う。** 現時点では設計のみでコードは無い
- **`ops-dev-environment-setup` スキルを実装後に書き直す**必要がある
  ([スキル一覧](../reference/skills-catalog.md))
- 並列作業の「触ってよいファイルの境界」は、このパッケージ境界で引く
