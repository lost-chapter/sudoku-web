## 設計の骨子(工程を読む前に)

```
packages/core       盤面ロジック(DOM も Node API も使わない)
packages/generator  問題を大量生成する CLI(Node)
packages/web        React + TypeScript のアプリ
puzzles/            生成された問題パック(外部ファイル)
```

- **問題は事前に生成してファイルへ置く**([ADR 0003](../decisions/0003-external-puzzle-files.md))
- **`core` は生成側と遊技側で共有する。** ソルバを 2 つ持たない
- **`core` は乱数を外から受け取る。** 同じシードから同じ問題ができること

## 難易度クラスの供給(2026-08-05 決着)

⚠️ **いま「難問」「最難関」は 1 問も作れない。** 手筋ソルバがレベル 1〜4 までなので、
それより難しい問題は**評価できないまま捨てられている**(生成した問題の 41.5%。
[検証](../reports/2026-08-05-difficulty-distribution.md))。

**裁定は次の 3 つ。**

### 1. 工程 2 の 6(パック出力)を先にやる

**3 クラスぶんは今すぐ配れる。**先に本物のパックを出せば、
[`puzzles/`](../../puzzles/README.md) の仮置き(同型変換で作った 3 問)が消え、
agent-c の工程 4 も本物のパックの上で進む。

### 2. そのあと工程 2 の 7 でレベル 5〜7 を足す

**捨てている 41.5% がそのまま在庫になる。**手筋を足せば上のクラスへ移るので、
生成の作り直しは要らない(パックの作り直しは数秒)。

⚠️ **手筋を足すと既存パックの難易度が変わる。** マニフェストの
`generatedWith.techniques` が目印になるので、**足したらパックを作り直す**
([問題ファイルの形式](../api/puzzle-file-format.md))。

### 3. UI の難易度はマニフェストから出す(クラスを固定で書かない)

**`manifest.json` の `totals` を見て、0 件のクラスは出さない(または選べなくする)。**

**理由**: クラスの供給は工程 2 の進み方で変わる。UI に 5 つを固定で書くと、
**手筋を足すたびに UI を直すことになる**。データ駆動にしておけば、
`totals` が埋まった時点で自動的に選べるようになる。

⇒ [画面構成と操作仕様](../ui/screens-and-interactions.md#難易度の選択) に反映済み。

## 並列化の単位と前提

**運用のルールは [並列エージェントの運用](parallel-agent-operations.md) にある。**
ここには「何を分割できるか」だけを書く。

**工程 1 は分割しない。** 全員の前提になるので 1 人で通す。

工程 2 以降の分割単位。**パッケージ境界と一致させる。**

| 系統 | 中身 | 着手の前提 |
|------|------|-----------|
| A. ソルバと生成 | `core` の 1〜4 + `generator` | 工程 1 |
| B. 難易度評価 | `core` の 5 | **A の 2(ソルバ)ができてから** |
| C. 盤面 UI | `web` の盤面・入力・状態管理 | 工程 1 と[問題ファイルの形式](../api/puzzle-file-format.md) |
| D. 問題の取得と保存 | `web` の fetch・localStorage | 同上 |

**B は A に依存する。** 手筋ソルバはソルバの土台の上に乗る。
**C と D は A の完成を待たない** —— ファイル形式が契約として決まっているので、
手書きの 1 問だけで UI を進められる。

## 未解決の課題(全体)

**調べれば分かるもの**をここへ書く。**調べても決まらないもの**は
[保留中の判断事項](../reference/pending-decisions.md) へ書く。

| # | 課題 | いつ分かるか |
|---|------|------------|
| 1 | 同梱パックを難易度ごとに何問にするか | **生成時間は判断材料にならない**(1,000 問で やさしい 4.2 秒 / ふつう 15 秒 / むずかしい 25 秒。[検証](../reports/2026-08-05-difficulty-distribution.md))。**残るはファイルサイズと配信の観点**で、工程 2 の 6 でバイト数を測って決める |
| 2 | 難易度クラスのしきい値 | **分布は実測した**(やさしい 40.3% / ふつう 11.4% / むずかしい 6.8% / **評価できない 41.5%**)。⚠️ **まだ閉じない。**41.5% はレベル 5 以降を実装すれば上のクラスへ移るので、移った後で見直す |
| 3 | 生成の性能(1 問あたりの所要時間) | ✅ **実測済み。**`node` 実行で **1 問 1.5 ms**(評価込み 1.7 ms)。⚠️ **Vitest 上で測ると 7.9 ms と 5 倍遅く出る**(module 境界の呼び出しが最適化されないため。[検証](../reports/2026-08-05-puzzle-generation-benchmark.md#-実行環境で数値が-57-倍変わる2026-08-05-追記))。**並列化を入れたら測り直す** |
| 4 | 極小性(手がかりを 1 つ消すと一意解でなくなる)を要件にするか | ✅ **要件にしてよい。**いまの穴あけは必ず極小になり、やめても速くならない([検証](../reports/2026-08-05-puzzle-generation-benchmark.md)) |
| 5 | **TypeScript を 7 系へ上げられるか** | typescript-eslint が対応してから。いまは 6 系に固定(上げると `pnpm lint` が落ちる) |
| 6 | Mantine の CSS 232 KB と JS を削れるか | **削れることは確認済み**(2026-08-05・agent-c)。`@mantine/core/styles/<部品>.layer.css` が配布されている。⚠️ **JS も gzip 102 KB へ増えた**(Modal / Switch)。**切り替えは工程 4 の終わり** |
| 7 | 375px でセルが 44px を保てるか | ✅ **閉じた(2026-08-05)。達成不能と判明。**基準を 2 段に改訂した —— 盤面のセルは **24px 以上**(WCAG 2.2 の最小)、入力パッドは **44px 以上**([画面構成と操作仕様](../ui/screens-and-interactions.md#押せる大きさ2026-08-05-に改訂)) |
| 8 | `countSolutions` に時間・ノード数の上限を付けるか | **外部由来の盤面を受け入れる段階で要る。**伝播が効かない盤面は約 2.2 秒かかる([検証](../reports/2026-08-05-search-solver-benchmark.md))。生成では踏まない形なので当面は不要 |
| 9 | **「難問」「最難関」のパックをどうするか** | ✅ **決着(2026-08-05・管理役)。**下記「難易度クラスの供給」を参照 |
