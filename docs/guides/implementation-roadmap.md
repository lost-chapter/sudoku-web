
## 難易度クラスの供給(2026-08-05 決着)

⚠️ **いま「難問」「最難関」は 1 問も作れない。** 手筋ソルバがレベル 1〜4 までなので、
それより難しい問題は**評価できないまま捨てられている**(生成した問題の 41.5%。
[検証](../reports/2026-08-05-difficulty-distribution.md))。

**裁定は次の 3 つ。**

### 1. 工程 2 の 6(パック出力)を先にやる

**3 クラスぶんは今すぐ配れる**。先に本物のパックを出せば、
[`puzzles/`](../../puzzles/README.md) の仮置き(同型変換で作った 3 問)が消え、
agent-c の工程 4 も本物のパックの上で進む。

### 2. そのあと工程 2 の 7 でレベル 5〜7 を足す

**捨てている 41.5% がそのまま在庫になる**。手筋を足せば上のクラスへ移るので、
生成の作り直しは要らない(パックの作り直しは数秒)。

⚠️ **手筋を足すと既存パックの難易度が変わる。** マニフェストの
`generatedWith.techniques` が目印になるので、**足したらパックを作り直す**
([問題ファイルの形式](../api/puzzle-file-format.md))。

### 3. UI の難易度はマニフェストから出す(クラスを固定で書かない)

**`manifest.json` の `totals` を見て、0 件のクラスは出さない(または選べなくする)。**

**理由**: クラスの供給は工程 2 の進み方で変わる。UI に 5 つを固定で書くと、
**手筋を足すたびに UI を直すことになる**。データ駆動にしておけば、
`totals` が埋まった時点で自動的に選べるようになる。

⇒ [画面構成と操作仕様](../ui/screens-and-interactions.md#難易度の選択) に反映済み。

## 並列化の単位と前提

**運用のルールは [並列エージェントの運用](parallel-agent-operations.md) にある。**
ここには「何を分割できるか」だけを書く。

**工程 1 は分割しない。** 全員の前提になるので 1 人で通す。

工程 2 以降の分割単位。**パッケージ境界と一致させる。**

| 系統 | 中身 | 着手の前提 |
|------|------|-----------|
| A. ソルバと生成 | `core` の 1〜4 + `generator` | 工程 1 |
| B. 難易度評価 | `core` の 5 | **A の 2(ソルバ)ができてから** |
| C. 盤面 UI | `web` の盤面・入力・状態管理 | 工程 1 と[問題ファイルの形式](../api/puzzle-file-format.md) |
| D. 問題の取得と保存 | `web` の fetch・localStorage | 同上 |

**B は A に依存する。** 手筋ソルバはソルバの土台の上に乗る。
**C と D は A の完成を待たない** —— ファイル形式が契約として決まっているので、
手書きの 1 問だけで UI を進められる。
