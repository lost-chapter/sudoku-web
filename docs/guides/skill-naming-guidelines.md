# スキル命名規則

このプロジェクト内でスキルを新規作成または改名するときは、必ず以下の命名規則に従う。
名前だけでスキルの責務を推測でき、領域ごとに一貫した並びになることを目的とする。

## 基本形式

スキル名は次の形式にする。

```
<開発領域>-<具体的な目的または作業>
```

例：

- `game-board-generation`
- `ui-keyboard-interaction`
- `test-fixture-generation`
- `ops-branch-merge`

## 使用可能な開発領域

スキルの主な責務に応じて、次の接頭辞から 1 つだけ選択する。

| 接頭辞 | 対象とする責務 |
|--------|----------------|
| `game-` | 数独のルール、盤面、生成、解法、難易度、ヒント |
| `ui-` | 画面、操作、入力、キーボード、アクセシビリティ |
| `api-` | 永続化、外部連携、エンドポイント、保存形式の契約 |
| `test-` | 単体テスト、結合テスト、回帰テスト、テストデータ |
| `perf-` | 性能測定、ベンチマーク、最適化、プロファイリング |
| `data-` | データ構造、変換、正規化、バリデーション |
| `arch-` | アーキテクチャ、モジュール構成、依存関係、責務設計 |
| `dev-` | TypeScript、実装規約、開発支援 |
| `docs-` | 仕様書、設計書、検証結果、ADR、ドキュメント生成 |
| `ops-` | CI、ビルド、デプロイ、実行環境、リリース、運用 |
| `meta-` | AI 開発フロー、スキル管理、プロンプトやルールの整備 |

## 命名ルール

- 英小文字とハイフンのみを使用する
- 単語の区切りにはハイフンを使用する
- 開発領域の接頭辞は必ず 1 つ付ける
- 名前からスキルの目的を推測できるようにする
- 原則として 2〜5 単語程度の簡潔な名前にする
- `helper`、`utility`、`common`、`misc`、`general` など、責務が曖昧な単語は避ける
- `skill`、`tool` など、スキルであることを示すだけの単語は付けない
- 使用する言語やフレームワークに固有のスキルでない限り、技術名を含めない
- プロジェクト名は、他のプロジェクトと区別する必要がある場合にだけ含める
- 既存スキルと責務が重複する場合は、新規作成せず既存スキルの拡張を検討する
- **ユーザーのグローバルスキル(`~/.claude/skills/`)と責務が重複しないか先に確認する。**
  同じことをするスキルを 2 つ持つと、どちらが最新か分からなくなる

## 接頭辞の選択基準

複数の領域に該当する場合は、スキルが最終的に達成する目的を基準に接頭辞を選択する。

例：

- 解法の速度を測定する
  → `perf-solver-benchmark`
- テスト用の盤面データを生成する
  → テストが主目的なら `test-board-fixture-generation`
- 盤面の入力値を検証する
  → 保存形式の契約が主目的なら `api-input-validation`、
    数独のルール判定が主目的なら `game-board-validation`

判断できない場合は、候補を勝手に確定せず、次の項目を提示して確認する。

1. 推奨するスキル名
2. 選択した接頭辞と理由
3. 代替候補
4. 既存スキルと重複する可能性

## 出力形式

スキル名を提案するときは、次の形式で出力する。

- スキル名：`<skill-name>`
- 開発領域：`<prefix>`
- 目的：スキルが担当する作業を 1 文で説明
- 命名理由：この接頭辞と名前を選んだ理由
- 代替候補：必要な場合のみ 1〜2 件

スキルを実際に作成する前に、名前がこの命名規則を満たしているか確認する。

## ドキュメントへの記載

スキルを新規作成・改名・削除したときは、コードだけでなくドキュメントも合わせて更新する。

- スキルを追加したら、[スキル一覧](../reference/skills-catalog.md) に 1 行追加する
  (スキル名・開発領域・目的・配置)
- スキルを改名・削除したときは、[スキル一覧](../reference/skills-catalog.md) の該当行を更新・削除する
- スキルの目的や責務が変わったときは、一覧の「目的」も実態に合わせて更新する

実装とドキュメントを常に一致させ、一覧と整合の取れた状態を保つこと。
