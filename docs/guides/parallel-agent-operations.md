# 並列エージェントの運用

複数のエージェント(セッション)で同時に開発を進めるときのルール。

- **何を分割できるか** — [ロードマップの「並列化の単位と前提」](implementation-roadmap.md#並列化の単位と前提)
- **いまの担当と進行中の作業** — [作業の引き継ぎ](handover.md)
- **worktree ごとの環境の用意** — `ops-dev-environment-setup` スキル

この文書は**どう運用するか**だけを扱う。分割の設計と現在の状態は上の 3 つにある。

## 実装は worktree、調査はサブエージェント

**実装を複数のサブエージェントに同時にやらせない。**

| | worktree(別セッション) | サブエージェント |
|---|---|---|
| ファイル衝突 | **物理的に起きない** | 同一ツリーを共有するので起きる |
| テスト・開発サーバ | 独立(`node_modules` もポートも別) | 相互干渉する |
| 途中の判断 | ユーザーへ仰げる | **仰げない** |
| 統合 | `ops-branch-merge` スキルで定型化済み | 不要 |

機能の実装は**方針を途中で変える必要が出る長時間の作業**である。
仕様の読み違いや設計の破綻に気づいた時点で舵を切る必要があり、
**途中でユーザーへ判断を仰げないサブエージェントには向かない**。

サブエージェントが向くのは**書き込みを伴わない調べもの**である。

- 既存コードの確認(呼び出し経路・依存の有無)
- ライブラリや API の仕様調査
- 複数のモジュールを横断する影響調査

## 担当の立て方

### 1. 共有ロジックをまたがせない

**共有するモジュールを跨ぐ分割をすると、同じコードを二重実装する。**

sudoku-web で共有される見込みがあるのは次の 3 つ。
**この単位は分けずに 1 担当へまとめる。**

| 系統 | 含むもの | 共有するもの |
|------|---------|-------------|
| 盤面ロジック | 生成 / 解法 / 難易度評価 / 検証 | 盤面のデータ構造と候補の計算 |
| 盤面 UI | 盤面表示 / セル入力 / メモ / 取り消し | 盤面の状態管理とキーボード操作 |
| 永続化 | 保存 / 復元 / 記録 | 保存形式の契約 |

**構成が決まったら、この表を実際のディレクトリ名で書き直すこと。**

### 2. 前提が揃っていない系統は「調査と方針提案」から始める

前提が未決のまま実装を割り当てると手待ちになる。**初期スコープを調査に限り、
実装可否の判断は管理役経由でユーザーへ上げる。**

判断を待たずに実装へ進むと、方針が覆ったときに丸ごと捨てることになる。

### 3. 担当を決めたら文書へ書く

[作業の引き継ぎ](handover.md) の「進行中の作業」へ、担当・内容・状態を書く。
**中断すると失われる文脈**をそこに残すのが目的なので、着手時に書いて随時直す。

## ブランチと作業場所

**ブランチの規約は [ブランチ戦略](branch-strategy.md) にまとめてある。**
ここでは作業場所だけを扱う。

| 項目 | 規約 |
|------|------|
| 作業場所 | `.claude/worktrees/agent-<x>-<hash>`。**Git 管理外**なので端末ごとに作り直す |
| 担当とブランチの対応 | [作業の引き継ぎ](handover.md) の体制表に書く |

**開発サーバのポートは worktree ごとに変える。** 同じポートで複数立てると衝突する。
割り当ては[体制表](handover.md#3-いまの体制)。用意の手順は `ops-dev-environment-setup` スキル。

## 触ってよいファイルの境界

**境界はパッケージ境界で引く**([ADR 0001](../decisions/0001-project-structure.md))。

| 対象 | 扱い | 担当 |
|------|------|------|
| `packages/core/src/` | **b が持つ**。c は読むだけ | agent-b |
| `packages/generator/src/` | **b が持つ** | agent-b |
| `packages/web/src/` | **c が持つ**。b は触らない | agent-c |
| `puzzles/packs/` | **b が生成して置く**。c は読むだけ | agent-b |
| ルートの設定(`package.json` / `pnpm-workspace.yaml` / `tsconfig.base.json` / ESLint / Prettier / CI) | **触らない**。変更が要るときは管理役へ上げる | agent-a |
| 各パッケージの `package.json` | **依存の追加は自分のパッケージだけ**。追加したら区切り報告で必ず伝える | 各自 |
| `tools/` | **管理役が持つ** | agent-a |
| ロードマップ・引き継ぎ | 全員が更新する(競合は解決しやすい) | 全員 |
| 判断が要る事項 | [保留中の判断事項](../reference/pending-decisions.md) へ全員が追記する | 全員 |
| ADR・アルゴリズム仕様・UI 仕様 | **実装で設計と食い違いが出たら、実装ではなく文書を直す前に管理役へ上げる** | 全員 |

⚠️ **`packages/core` は b が持つが、c も使う。**
c が `core` に足りない関数を見つけたら、**自分で足さずに b へ依頼する**。
両方が同じ関数を実装すると、生成側と遊技側でロジックが割れる
([システム構成](../architecture/system-architecture.md))。

⚠️ **[問題ファイルの形式](../api/puzzle-file-format.md) は b と c の契約である。**
**片方の都合で変えない。** 変更が要るときは管理役へ上げ、両者が合意してから直す。

**既存の共有関数を変えると、他の担当が通していたテストを崩す。**
変えたときは自分の担当だけでなくテストを全件回して確認する。

## 着手前に必ずやること

1. **読む順序を守る** — [AGENTS.md](../../AGENTS.md) → [作業の引き継ぎ](handover.md) →
   [実装の進め方と現在地](implementation-roadmap.md)
2. **現在地を実測する** — 文書の数値を信用せず、テストとビルドを回してから始める
   ([引き継ぎの「現在地を実測で確かめる」](handover.md#2-現在地を実測で確かめる))
3. **自分の担当の前提が揃っているか確かめる** — 未決の判断に依存していないか
   ([保留中の判断事項](../reference/pending-decisions.md))

## 進捗の測り方と報告

**進捗は主観で語らず数値で出す。**

- テストの件数と成否
- 型チェック・Lint のエラー数
- 段階分割してある作業は段階表の到達点

報告に必ず含めること。

| 項目 | 理由 |
|------|------|
| **何ができるようになったか**(動く経路・通ったテスト) | 「実装した」だけでは動くか分からない |
| **残っている問題の機序** | 推測と実測を区別して書く |
| **判断待ちが出たか** | 出たら [保留中の判断事項](../reference/pending-decisions.md) へ足す |

### ⚠️ 「どのコミットか」を確かめても、「いつの時点か」は揃わない(2026-08-06)

**作業エージェントが「未統合 4 件」と報告してきた。実際には 0 件だった。**

⚠️ **確かめ方は合っていた。** `git log --oneline -1 develop` を並べて送っていた。
**その値自体が、報告を書いた時点のものだった。**
**管理役はその報告を受けてマージしたので、届いたときには古くなっていた。**

🎯 **並行して動いている以上、作業エージェントの側からは原理的に確かめきれない。**
**送った瞬間に古くなる。**

**⇒ 直し方は「もっとよく確かめる」ではない。**

| 誰が | 何をする |
|------|---------|
| 作業エージェント | **食い違ったら、直さずに送る。**「私の側では N 件に見えます」と値を添えて |
| 管理役 | **受けたら実測して返す。**⚠️ **相手の値を否定するのではなく、いまの値を出す** |

⚠️ **報告に時点を書いてもらっても解決しない。** 読む側が突き合わせる手間が増えるだけである。
**「食い違ったら送る」で足りる。**

### 🎯 食い違いが出たら、まず自分の測り方を見る

**相手の値を疑うほうが自然な反応である。⚠️ 意識しないと逆をやる。**

**2026-08-06 の 1 日で、食い違いから見つかった測り方の誤りは 4 件あった。**

| 誤り | 誰の | 自分の測定だけを見ていたら |
|------|------|------------------------|
| `.first()` が入力のたび別のセルを指す | 管理役 | **例外も出ず、嘘の結果だけが返る** |
| 合成した `TouchEvent` が `click` の有無ごと消していた | 作業 | **「20px は確定入力」と報告していた** |
| `element.click()` で `mousedown` が出ない | 作業 | **「モーダルが開かない」という嘘の欠陥** |
| `\| tail` で終了コードを隠す | **両方** | **落ちた検査を「通った」と報告する** |

🎯 **4 件とも「通っているように見える」形で失敗していた。**
**気づけたのは毎回「相手の値と食い違ったとき」である。**

**⇒ 食い違いを、相手の間違いを探す合図ではなく、
自分の測り方を見直す合図として使う。** そのほうが早い。

### ⚠️ 食い違いを待たなくてよい ——「どう測ったか」を聞くだけで足りる

**上の 4 件のうち 1 件は、値が食い違う前に見つかった。**
**報告された数値を疑ったのではなく、「その値はどう測りましたか」と聞いただけである。**

🎯 **聞かれた側は、そこで初めて「値が合っていること」と
「測り方が正しいこと」を分けて考えた。**
**⚠️ 自分では分けて考えていなかった** ——
**本番でも同じ値が出た時点で、終わりにするところだった。**

**⇒ 数値の報告を受けたら、値の妥当性ではなく「取り方」を 1 つ聞く。**
**食い違っていなくても聞く。** 食い違いが出るのを待つより早く、
**食い違わない種類の誤り**(たまたま同じ値が出る)も捕まる。

### 🎯 管理役は進捗の一枚絵を保つ(2026-08-06 に追加)

**[進捗の一枚絵](../assets/progress.html) を管理役が持ち、統合のたびに更新する。**

**なぜ要るか。** 進捗は
[ロードマップ](implementation-roadmap.md)・[引き継ぎ](handover.md)・
[保留中の判断事項](../reference/pending-decisions.md) に分かれて書いてある。
**正本としてはそれで正しいが、「いま何が止まっているか」を知るのに 3 つ読むことになる。**

| 何を出すか | なぜ |
|-----------|------|
| **工程の帯**(0〜6)と現在地 | 全体のどこにいるかを 1 行で |
| **いまの工程の内訳**(担当・状態・備考) | 誰が何で止まっているか |
| **未解決**(重い順) | ⚠️ **最優先のものが最初に目へ入ること** |
| 体制(誰が何を持っているか) | 声を掛ける先が分かる |
| 数値(テスト・CI・未プッシュ) | 主観を挟まない |

⚠️ **更新の引き金は「統合したとき」と「差し戻したとき」。**
**作業を始めたときではない**。始めた時点では、まだ何も動いていない。

⚠️ **一枚絵は要約であって正本ではない。**
**判断の根拠は必ず正本の側に書き、一枚絵からは参照するに留める。**
**二重に持つと、片方が必ず古くなる。**

**区切りは `/compact` を掛けるタイミングである。**
「コミット済み・worktree クリーン・管理役への区切り報告を送信済み」の状態で掛け、
次の作業単位をきれいなコンテキストで始める。
**`/compact` は Claude Code の組み込みコマンドで、実行できるのはユーザーだけ**
(エージェントが呼べるツールとしては提供されていない)。
エージェントは区切り報告に「`/compact` 可能」と添え、実行はユーザーが行う。
掛からなくても、長くなればハーネスの自動圧縮が走るので作業は途切れない。

## 統合

**機能単位(段階分割なら段階単位)で寄せる。大きく溜めない。**
溜めるほど共有ロジックの競合が増え、どちらの変更が不具合の原因か分からなくなる。

**誰も他人のブランチを直接書き換えない。**

**統合の流れと権限は [ブランチ戦略](branch-strategy.md) にまとめてある。**
要点は 2 つ。**`cc/agent-*` → `feature/agent-a` → `develop` の 2 段で寄せる**こと、
**`develop` へ直接コミットしない**こと。

手順は `ops-branch-merge` スキル(作業ブランチを統合先へ no-ff マージし、
最後に作業ブランチを fast-forward して同一コミットへ揃える)。

統合したあと**管理役がやること**。

1. テスト・型チェック・ビルドを回して**実測する**
2. **ロードマップの数値を実測値へ直す。**
   テスト件数は、**各自の手元の値を足しても合わない**
3. ドキュメントが競合したら**両方の記述を残す**(片方を消さない)

## 決めたことは文書へ落とす

**セッション間でやり取りした判断は Git に残らない。**
「会話で説明したから大丈夫」は引き継ぎでは成立しない。
置き場所は [引き継ぎの「コミットされていない知識も落ちる」](handover.md#コミットされていない知識も落ちる) にある。

## 禁止事項

- **プッシュは指示があるまでしない**([AGENTS.md](../../AGENTS.md) の開発上の約束)
- **他人のブランチを直接書き換えない**
- **`develop` へ直接コミットしない**([ブランチ戦略](branch-strategy.md))
- **`develop` へ作業エージェントがマージしない**(管理役だけ)
- **実装を複数のサブエージェントへ同時に割り当てない**(上記「実装は worktree」)
- **共有モジュールの既存関数を相談なく変えない**

## よくある落とし穴

- **共有ロジックを 2 人が同時に変える**: 追加なら安全だが、既存関数の変更は
  他の担当のテストを崩す。変更前に管理役へ相談する
- **統合を溜める**: 機能単位で寄せる。溜めると不具合の切り分けができない
- **数値を足して報告する**: テスト件数はマージ後に実測しないと合わない
- **判断待ちを会話に置く**: [保留中の判断事項](../reference/pending-decisions.md) へ書かないと消える
- **worktree にメインの準備が効いていると思い込む**: `node_modules`・`.env`・
  `.claude/settings.local.json` は **worktree ごとに要る**
- **開発サーバのポートが衝突する**: worktree ごとに変える
