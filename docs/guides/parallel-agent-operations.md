# 並列エージェントの運用

複数のエージェント(セッション)で同時に開発を進めるときのルール。

- **何を分割できるか** — [ロードマップの「並列化の単位と前提」](implementation-roadmap.md#並列化の単位と前提)
- **いまの担当と進行中の作業** — [作業の引き継ぎ](handover.md)
- **worktree ごとの環境の用意** — `ops-dev-environment-setup` スキル

この文書は**どう運用するか**だけを扱う。分割の設計と現在の状態は上の 3 つにある。

## 実装は worktree、調査はサブエージェント

**実装を複数のサブエージェントに同時にやらせない。**

| | worktree(別セッション) | サブエージェント |
|---|---|---|
| ファイル衝突 | **物理的に起きない** | 同一ツリーを共有するので起きる |
| テスト・開発サーバ | 独立(`node_modules` もポートも別) | 相互干渉する |
| 途中の判断 | ユーザーへ仰げる | **仰げない** |
| 統合 | `ops-branch-merge` スキルで定型化済み | 不要 |

機能の実装は**方針を途中で変える必要が出る長時間の作業**である。
仕様の読み違いや設計の破綻に気づいた時点で舵を切る必要があり、
**途中でユーザーへ判断を仰げないサブエージェントには向かない**。

サブエージェントが向くのは**書き込みを伴わない調べもの**である。

- 既存コードの確認(呼び出し経路・依存の有無)
- ライブラリや API の仕様調査
- 複数のモジュールを横断する影響調査

## 担当の立て方

### 1. 共有ロジックをまたがせない

**共有するモジュールを跨ぐ分割をすると、同じコードを二重実装する。**

sudoku-web で共有される見込みがあるのは次の 3 つ。
**この単位は分けずに 1 担当へまとめる。**

| 系統 | 含むもの | 共有するもの |
|------|---------|-------------|
| 盤面ロジック | 生成 / 解法 / 難易度評価 / 検証 | 盤面のデータ構造と候補の計算 |
| 盤面 UI | 盤面表示 / セル入力 / メモ / 取り消し | 盤面の状態管理とキーボード操作 |
| 永続化 | 保存 / 復元 / 記録 | 保存形式の契約 |

**構成が決まったら、この表を実際のディレクトリ名で書き直すこと。**

### 2. 前提が揃っていない系統は「調査と方針提案」から始める

前提が未決のまま実装を割り当てると手待ちになる。**初期スコープを調査に限り、
実装可否の判断は管理役経由でユーザーへ上げる。**

判断を待たずに実装へ進むと、方針が覆ったときに丸ごと捨てることになる。

### 3. 担当を決めたら文書へ書く

[作業の引き継ぎ](handover.md) の「進行中の作業」へ、担当・内容・状態を書く。
**中断すると失われる文脈**をそこに残すのが目的なので、着手時に書いて随時直す。

## ブランチと作業場所

| 項目 | 規約 |
|------|------|
| ブランチ名 | `cc/agent-<x>`(Claude Code の worktree 機能が作る既定の形) |
| 作業場所 | `.claude/worktrees/agent-<x>-<hash>`。**Git 管理外**なので端末ごとに作り直す |
| 統合先 | `feature/agent-a`(管理役が寄せる)→ まとまったら `develop`(下記「統合」) |

管理役のブランチは慣例で `feature/agent-a` を使う。名前は問わないが、
**どのブランチがどの担当かを [作業の引き継ぎ](handover.md) の体制表に書く**こと。

**開発サーバのポートは worktree ごとに変える。** 同じポートで複数立てると衝突する。
用意の手順は `ops-dev-environment-setup` スキル。

## 触ってよいファイルの境界

**実装がまだ無いため、境界表はこれから埋める。** 分割の設計ができた時点で、
「新規作成してよい場所」「1 行追加だけ許す場所」「触らない場所」を表にする。

それまでの暫定の原則は次の 3 つ。

- **自分の担当のディレクトリの中は自由。** 他人のディレクトリは触らない
- **共有モジュール(盤面のデータ構造・状態管理・共通コンポーネント)への追加は自由。
  既存関数の変更は管理役へ先に相談する**
- **設定ファイル(ビルド設定・依存パッケージ・CI)は同時に触らない。**
  追加する担当を一時的に 1 人へ寄せる

| 対象 | 扱い |
|------|------|
| ロードマップ・引き継ぎ | 全員が更新する(競合は解決しやすい) |
| 判断が要る事項 | [保留中の判断事項](../reference/pending-decisions.md) へ全員が追記する |

**既存の共有関数を変えると、他の担当が通していたテストを崩す。**
変えたときは自分の担当だけでなくテストを全件回して確認する。

## 着手前に必ずやること

1. **読む順序を守る** — [AGENTS.md](../../AGENTS.md) → [作業の引き継ぎ](handover.md) →
   [実装の進め方と現在地](implementation-roadmap.md)
2. **現在地を実測する** — 文書の数値を信用せず、テストとビルドを回してから始める
   ([引き継ぎの「現在地を実測で確かめる」](handover.md#2-現在地を実測で確かめる))
3. **自分の担当の前提が揃っているか確かめる** — 未決の判断に依存していないか
   ([保留中の判断事項](../reference/pending-decisions.md))

## 進捗の測り方と報告

**進捗は主観で語らず数値で出す。**

- テストの件数と成否
- 型チェック・Lint のエラー数
- 段階分割してある作業は段階表の到達点

報告に必ず含めること。

| 項目 | 理由 |
|------|------|
| **何ができるようになったか**(動く経路・通ったテスト) | 「実装した」だけでは動くか分からない |
| **残っている問題の機序** | 推測と実測を区別して書く |
| **判断待ちが出たか** | 出たら [保留中の判断事項](../reference/pending-decisions.md) へ足す |

**区切りは `/compact` を掛けるタイミングである。**
「コミット済み・worktree クリーン・管理役への区切り報告を送信済み」の状態で掛け、
次の作業単位をきれいなコンテキストで始める。
**`/compact` は Claude Code の組み込みコマンドで、実行できるのはユーザーだけ**
(エージェントが呼べるツールとしては提供されていない)。
エージェントは区切り報告に「`/compact` 可能」と添え、実行はユーザーが行う。
掛からなくても、長くなればハーネスの自動圧縮が走るので作業は途切れない。

## 統合

**機能単位(段階分割なら段階単位)で寄せる。大きく溜めない。**
溜めるほど共有ロジックの競合が増え、どちらの変更が不具合の原因か分からなくなる。

**誰も他人のブランチを直接書き換えない。**

**統合の流れは 2 段である。**

```
cc/agent-* ──(区切りの報告が来たら管理役が即座に)──▶ feature/agent-a
feature/agent-a ──(実装がまとまった時点で管理役が)──▶ develop
```

- **作業エージェントのブランチ(`cc/agent-*`)は、まず `feature/agent-a` へ集約する。**
  区切りの報告が来たら管理役が即座に寄せる
- **`develop` へは、ある程度の実装が `feature/agent-a` にまとまった時点で**
  管理役がマージする。細かい文書修正のたびに寄せない
- **`develop` へマージできるのは管理役だけ。**
  作業エージェントは `develop` を**読む(自分のブランチへ取り込む)だけ**とし、
  `develop` をチェックアウトしてのマージ・コミットをしない

手順は `ops-branch-merge` スキル(作業ブランチを統合先へ no-ff マージし、
最後に作業ブランチを fast-forward して同一コミットへ揃える)。

統合したあと**管理役がやること**。

1. テスト・型チェック・ビルドを回して**実測する**
2. **ロードマップの数値を実測値へ直す。**
   テスト件数は、**各自の手元の値を足しても合わない**
3. ドキュメントが競合したら**両方の記述を残す**(片方を消さない)

## 決めたことは文書へ落とす

**セッション間でやり取りした判断は Git に残らない。**
「会話で説明したから大丈夫」は引き継ぎでは成立しない。
置き場所は [引き継ぎの「コミットされていない知識も落ちる」](handover.md#コミットされていない知識も落ちる) にある。

## 禁止事項

- **プッシュは指示があるまでしない**([AGENTS.md](../../AGENTS.md) の開発上の約束)
- **他人のブランチを直接書き換えない**
- **`develop` へ作業エージェントがマージしない**(管理役だけ)
- **実装を複数のサブエージェントへ同時に割り当てない**(上記「実装は worktree」)
- **共有モジュールの既存関数を相談なく変えない**

## よくある落とし穴

- **共有ロジックを 2 人が同時に変える**: 追加なら安全だが、既存関数の変更は
  他の担当のテストを崩す。変更前に管理役へ相談する
- **統合を溜める**: 機能単位で寄せる。溜めると不具合の切り分けができない
- **数値を足して報告する**: テスト件数はマージ後に実測しないと合わない
- **判断待ちを会話に置く**: [保留中の判断事項](../reference/pending-decisions.md) へ書かないと消える
- **worktree にメインの準備が効いていると思い込む**: `node_modules`・`.env`・
  `.claude/settings.local.json` は **worktree ごとに要る**
- **開発サーバのポートが衝突する**: worktree ごとに変える
