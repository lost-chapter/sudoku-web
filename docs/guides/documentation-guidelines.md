# ドキュメント管理規則

プロジェクト内のドキュメントは、原則としてすべて `docs/` 配下に格納する。
ドキュメントを作成・移動・更新するときは、内容に応じたカテゴリへ分類し、利用者が目的の情報を容易に見つけられる構成を維持する。

## 基本方針

- ドキュメントをリポジトリ直下やソースコード内へ無秩序に配置しない
- 各ドキュメントは、最も主要な目的に対応するカテゴリへ 1 つだけ配置する
- 同じ内容を複数のカテゴリへ重複して保存しない
- 関連する別のドキュメントは、複製せず相対リンクで参照する
- 新しいカテゴリを安易に追加せず、まず既存カテゴリへ分類できないか検討する
- 一時的なメモや作業途中の文書は、正式なドキュメントと区別する
- 実装変更によって内容が古くなった場合は、関連ドキュメントも同時に更新する

### 🎯 反証できる形で書く(2026-08-05 に追加)

**曖昧に書いて誰も反証できない状態のほうが、具体的に間違えるより危ない。**

2026-08-05 に管理役の設計文書の誤りが 3 件見つかったが、**どれも
「実装したら必ずどちらかを選ばされる形」で書いてあったから表に出た**。

| 書いてあったこと | 実装した人が踏んだこと |
|----------------|--------------------|
| 「各ワーカーへ別々のシードを配る」 | 並列度を変えると中身が変わり、再現性の前提が壊れる |
| 「200 問版は先頭 200 行と一致する」 | 実際は 169 行が相違(パックはスコア昇順で書くため) |
| 適用順が別の文書のレベル表と食い違う | 手筋を順に試す実装で、どちらに従うか選ばされる |

**抽象的に書いていれば、実装した人はどちらかへ勝手に寄せ、誰も気づかないまま進む。**

⇒ **数値・順序・条件は、外れていれば実測で否定できる形で書く。**
「適切に」「必要に応じて」で濁さない。

### 🎯 和文で強調を閉じるとき、句点を強調の内側に入れない(2026-08-06 に追加)

**`**完了。**次へ` と書くと強調が効かず、`**` が画面にそのまま出る。**

2026-08-06 の実測で、`docs/` 28 文書のうち **17 文書・89 か所**がこの形だった。

#### なぜそうなるか

CommonMark は、区切り(`**`)が**閉じ**になれるかを前後の文字の種類で決める(flanking 規則)。
閉じになれるのは、**直前が空白でなく**、かつ
**「直前が約物でない」か「直後が空白か約物である」** ときに限る。

`**完了。**次へ` は**直前が「。」(約物)で、直後の「次」が空白でも約物でもない**ため、
この `**` は閉じになれない。行き場を失った記号がそのまま本文に出る。

⚠️ **これは特定のツールの癖ではない。** GitHub(cmark-gfm)でも同じに壊れる。

#### どう書けば通るか

**約物を強調の外へ出す。** これだけでよい。

| 書き方 | 素の CommonMark |
|-------|----------------|
| `**完了(2026-08-05)。**5 クラス` | ❌ `**` が出る |
| `**完了(2026-08-05)**。5 クラス` | ✅ 効く |
| `` **`core` を直す。**次へ `` | ❌ `**` が出る |
| `` **`core` を直す**。次へ `` | ✅ 効く |
| `**完了(2026-08-05)。** 5 クラス` | ✅ 効く(直後が空白なら閉じられる) |

#### 変換側は救っている。ただし `.md` を読む人は救われない

`docs-html` の変換には**全角文字に隣接する区切りを開き・閉じとして認める緩和**が入っている
(2026-08-06)。HTML では 89 か所とも強調される。

**しかし GitHub とエディタのプレビューでは壊れたままである。**
⇒ **新しく書く文章では上の書き方に従う。**

#### 守れているかは機械で見る(2026-08-06 に追加)

**この節を書いた後に書かれた文章で、さらに 8 か所が同じ形で壊れていた。**
⇒ **人が気をつける話をやめ、検査にした。**

```bash
node tools/docs-lint/check-emphasis.mjs      # 閉じられない `**` を挙げる
```

見つかった行がそのまま出る。直し方は上の表のとおり。
方針は [テストの方針](../verification/testing-policy.md) の
「和文の強調は機械で見張る」にある。

#### ⚠️ まとめて直すときは、開きと閉じを数えること(2026-08-06 に追記)

**`**` は開きも閉じも見た目が同じなので、前後の文字だけでは判断できない。**

2026-08-06 に 128 か所を直したとき、**開閉を区別しない一括置換**を先に流して壊した。

```
- 数独を遊べる Web アプリケーション。**問題は事前に生成して…**
+ 数独を遊べる Web アプリケーション**。問題は事前に生成して…**   ← 開きの前の句点を動かした
```

⇒ **行の頭から `**` を数え、「いま開いているか」を持ちながら、閉じの直前だけを動かす。**
⚠️ **コードスパンとコード塊は対象外にする**(この節の表がまさに壊れた書き方を例示している)。

**直したあとは「何も失っていない」ことを確かめる。**

| 検査 | 見ているもの |
|------|------------|
| `<strong>` の数が減っていない | 強調が消えていないか。⚠️ **数が同じでも別の場所が強調されている可能性は残る** |
| HTML に出る `**` の数 | 記号が残っていないか。⚠️ **消えたことしか見ていない** |
| 🎯 **タグと空白を除いた本文が完全に一致する** | ⚠️ **「何も失っていない」を直接示せる**。約物を動かしただけなら本文は変わらない |

**閉じ括弧(`」` `)`)が直前にあるときは、外へ出さず「閉じの直後に空白」を使う。**
外へ出すと、強調の中に残る開き括弧と対にならなくなる。

### 🎯 図は mermaid と ASCII を使い分ける(2026-08-06 に追加)

**mermaid で描けることは、mermaid で描いたほうがよい図の条件ではない。**

`docs/` の図は ` ```mermaid ` で書ける([HTML 変換](#ドキュメントを-html-で読む)がビルド時に SVG へ直し、
GitHub とエディタは記法をそのまま描く)。⚠️ **ただし ASCII の図が勝つ形がある。**

| 形 | 向いている書き方 | 理由 |
|----|----------------|------|
| 直列の流れ・分岐・合流 | **mermaid** | 層に分けて自動で並ぶ。箱と矢印で関係が一意に読める |
| **木構造**(ディレクトリツリー) | **ASCII** | `├──` は木を表す記法として完成している。mermaid は縦に伸ばすだけ |
| **左右対称の構造** | **ASCII** | 自動配置は上から下へ層を作るので、**対称性が保てない** |
| 情報密度が要るところ | **ASCII** | mermaid の箱は余白を持つ。同じ内容で 2 倍近い高さになる |

**2026-08-06 の実例。** [システム構成](../architecture/system-architecture.md) の全体像
(2 つの側が 1 つの `core` を共有する図)を mermaid にしたが、**ASCII へ戻した**。

- **`[ 作る側 ]` `[ 遊ぶ側 ]` という枠組みが、ノードのラベルの括弧へ落ちた**(意味の劣化)
- **対称だった形が縦一列になり、片方だけが遠回りする線になった**
- 高さが 230px から 430px へ増えた

⇒ 🎯 **僅差なら置き換えない。**⚠️ **記法として完成しているものを、新しい道具で置き換える理由はない。**

**迷ったら両方を出して並べる。**⚠️ **頭の中で比べない。**

#### ⚠️ 横長の図は縮んで、文字が本文より小さくなる

**HTML 側の図は本文の幅に収まるよう自動で縮む。**
**横に長い図は縮尺が下がり、図の文字だけが読めなくなる。**

**2026-08-06 の実測。** ブランチ戦略の図を横(`flowchart LR`)で描いたところ、
**縮尺 0.75・図の文字が 10px**(本文は 16px)になった。**縦(`TB`)にすると等倍で収まった。**

#### ⚠️ 確かめる幅は 1280px。図の幅は 520px までに収める

**「縮まない」は測った窓の幅で変わる。**⚠️ **1440px で等倍でも、1280px では縮むことがある**
(画面遷移の図が 641px で、**1440px は等倍・1280px は 0.872** だった)。

| 決めごと | 値 |
|---------|-----|
| **確かめる幅** | **1280px**(小さめのノート PC)。ここで等倍なら、より広い画面でも等倍 |
| **図の幅の上限** | **520px**。1280px の本文欄は約 555px |

**幅が超えたときの直し方**(効く順)。

1. **長いラベルを `<br/>` で 2 行にする** —— 「難易度を選ぶ / 続きから」で 641px → 520px
2. **向きを変える**(`LR` → `TB`)
3. **ノードを減らす**(その図で言いたいことに絞る)

⇒ **図を足したら `pnpm docs:html` で開き、図の文字が本文より小さくなっていないか確かめる。**

## 標準ディレクトリ構成

```
docs/
├── README.md
├── overview/
├── architecture/
├── algorithms/
├── ui/
├── api/
├── verification/
├── decisions/
├── guides/
├── reference/
├── reports/
└── assets/
```

## カテゴリの用途

### `docs/README.md`

ドキュメント全体の入口。次の情報を記載する。

- 各カテゴリの説明
- 主要ドキュメントへのリンク
- 初めて参加する開発者が読む順序
- 現在進行中の検証や重要な設計判断へのリンク

ドキュメントを追加・移動・削除した場合は、必要に応じてこのファイルのリンクも更新する。

### `docs/overview/`

プロジェクト全体の概要を格納する。例：

- プロジェクトの目的
- 対象範囲と対象外
- 用語集(セル・ブロック・候補・ヒントなど、数独の用語を含む)
- 開発方針

### `docs/architecture/`

システム構成や設計方針を格納する。例：

- 全体アーキテクチャ
- モジュール構成(ロジックと UI の境界)
- 状態管理の方針
- データフロー
- 依存関係
- エラーハンドリング方針

### `docs/algorithms/`

数独のロジックの仕様や検討内容を格納する。例：

- 盤面の生成
- 解法(解探索、候補の絞り込み)
- 一意解の判定
- 難易度の評価
- ヒントの提示
- 入力の検証(重複・矛盾の検出)

1 つの文書に複数の無関係なアルゴリズムをまとめず、原則としてテーマごとに分割する。

### `docs/ui/`

画面と操作の仕様を格納する。例：

- 画面構成と遷移
- 盤面の操作仕様(選択・入力・メモ・取り消し)
- キーボード操作とショートカット
- アクセシビリティ方針
- レスポンシブ・タッチ操作の方針

**見た目の実装ではなく仕様を書く。** コンポーネントの実装詳細はコード側の責務とし、
ここには「何をどう振る舞わせるか」を残す。

### `docs/api/`

永続化と外部連携の仕様を格納する。例：

- エンドポイント仕様(サーバを持つ場合)
- リクエストとレスポンス
- 保存形式の契約(ローカル保存を含む)
- エラー形式
- 入出力例

**サーバを持たない構成に決まった場合も、保存形式の契約はここへ置く。**
データ形式そのものの一覧は `docs/reference/` と使い分ける。

### `docs/verification/`

検証方法、検証条件、期待値を格納する。例：

- テストケース設計
- 生成した盤面が満たすべき条件(解が一意など)
- 性能評価方法
- 合否判定基準

検証方法ではなく、実際に実施した検証の結果は `docs/reports/` に格納する。

### `docs/decisions/`

重要な設計判断を ADR 形式で格納する。ファイル名は次の形式にする。

```
NNNN-<decision-title>.md
```

例：

```
0001-use-typescript.md
0002-board-state-representation.md
```

各 ADR には、少なくとも次の項目を記載する。

- ステータス
- 背景
- 決定内容
- 判断理由
- 採用しなかった選択肢
- 影響

### `docs/guides/`

開発者向けの手順書を格納する。例：

- 開発環境の構築
- ローカルでの実行
- テストの実行
- リリース手順
- 並列で作業するときの運用

### `docs/reference/`

頻繁に参照する事実情報や一覧を格納する。例：

- 用語の詳細
- データ形式
- 定数一覧
- 対応機能一覧
- スキル一覧
- 保留中の判断事項

### `docs/reports/`

実施済みの調査、実験、検証、ベンチマークの結果を格納する。
時系列で区別する必要がある文書は、次の形式で命名する。

```
YYYY-MM-DD-<report-title>.md
```

例：

```
2026-08-05-solver-benchmark.md
2026-08-05-difficulty-rating-survey.md
```

各レポートには、可能な範囲で次の項目を記載する。

- 目的
- 実施日
- 対象バージョンまたはコミット
- 条件
- 使用データ
- 結果
- 考察
- 結論
- 残課題

### `docs/assets/`

ドキュメントから参照する画像、図、添付データを格納する。
可能であればカテゴリ別のサブディレクトリを作成する。例：

```
docs/assets/architecture/
docs/assets/ui/
docs/assets/reports/
```

## ファイル命名規則

- Markdown ファイルは原則として `.md` を使用する
- ファイル名には英小文字、数字、ハイフンを使用する
- 単語の区切りにはハイフンを使用する
- **例外**: 共有を目的とした読み物(図解資料や非エンジニア向けの説明)は、
  受け取る人がファイル名で内容を判断できるよう**日本語のファイル名を使う**。
  日付の規則(レポートの `YYYY-MM-DD-`)は日本語名でも維持する
- 内容が分からない名前を避ける
- `document.md`、`memo.md`、`new.md`、`temp.md`、`misc.md` などの曖昧な名前を使用しない
- 日付に意味があるレポート以外には、不要な日付を付けない
- バージョン管理で追跡できるため、`final`、`latest`、`v2` などを安易に付けない

良い例：

```
board-generation.md
difficulty-rating.md
keyboard-operations.md
```

避ける例：

```
document1.md
new-spec.md
solver-final-v2.md
```

## ドキュメントを HTML で読む

**Markdown のままでは読みにくい場面がある**(長い文書を通しで読む、Markdown を読まない人へ渡す、
印刷する)。そのために `docs-markdown-to-html` スキルで `docs/` を HTML のサイトへ変換する。

```bash
pnpm docs:html      # docs/ → docs-html/。入口は docs-html/index.html
```

**出力は `docs-html/` に閉じる。`docs/` の隣に生成物を置かない。**
構造は `docs/` と同じなので、文書間の相対リンクと添付への参照がそのまま効く。

HTML 側には、Markdown のままでは得られないものを載せている。

- **サイドメニュー**(全文書の一覧・カテゴリ別・絞り込み)でどこへでも移動できる
- **ページ内の目次**が、いま読んでいる節を追いかける
- 見出しへのリンク・コードのコピー・前後のドキュメントへの導線・テーマ切替

**この変換は純粋関数として扱う。**

- 同じ `docs/` からは**いつでも同じ出力**ができる(生成日時などを埋め込まない)
- 入力の `.md` を**書き換えない**
- CSS と JS は**インライン**で、外部 CDN に依存しない(オフラインで開ける)
- **入力は `docs/` のツリー全体である。** サイドメニューが一覧を持つため、
  文書を 1 つ足すと全ページが変わる(壊れではない)

**生成された `docs-html/` は Git 管理外とする。**

- **正本は常に `docs/` の `.md` である。** `docs-html/` は再生成できる派生物にすぎない
- **`.html` を編集しない。** 直すのは `.md` の側
- **`docs-html/` をコミットしない。** `git add -f` で強制追加もしない
- レビュー・差分・引用の対象は `.md`

手順とコマンドは [`docs-markdown-to-html` スキル](../../.claude/skills/docs-markdown-to-html/SKILL.md) にある。

## ドキュメント作成時の手順

ドキュメントを作成するときは、次の順序で判断する。

1. 文書の主な目的を特定する
2. 標準カテゴリから配置先を 1 つ選択する
3. 同じ目的の既存ドキュメントがないか確認する
4. 既存文書へ追記すべきか、新しい文書に分割すべきか判断する
5. 命名規則に従ってファイル名を決める
6. 関連ドキュメントへの相対リンクを追加する
7. `docs/README.md` またはカテゴリ内の索引を更新する
8. リンク切れや内容の重複がないことを確認する

配置先を判断できない場合は、勝手にカテゴリを新設せず、以下を提示する。

- 文書の目的
- 推奨する配置先
- 推奨理由
- 代替の配置先
- 新しいカテゴリが本当に必要かどうか

ドキュメントの作成だけでなく、実装変更時にも関連文書への影響を確認し、コードとドキュメントの整合性を維持する。
